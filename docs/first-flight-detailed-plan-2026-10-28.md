**수용 기준:** 실제 장치로 축/방향·저장→재실행→연결·비행·손실/복구를 확인한다. fixture 검사는 별도로 표시한다. 설정 완료 시간·되돌아간 단계·도움을 요청한 지점은 사용성 관찰로 기록하되 사전에 근거 없는 성공률이나 시간 목표를 확정하지 않는다.

## 4. 한국어 문구와 접근성 — UX-01/03/05/06/07/10/12

- 용어 초안: “연결”, “설정 저장”, “비행 준비”, “모터 시작(ARM)”, “모터 정지(DISARM)”. ARM/DISARM은 전원 켜기/끄기와 혼동하지 않게 도움말에서 구분한다.
- 한 문장에 한 행동을 안내한다. 버튼은 “다음”, “다시 확인”, “저장”, “취소”처럼 실제 동작과 맞춘다.
- 거부 사유 예: “스로틀을 최저로 내려 주세요”, “조종기 입력을 확인할 수 없어요”, “먼저 보정을 완료해 주세요”. **실제 거부 원인에 맞을 때만** 표시한다.
- 복수 오류는 우선 해결할 안전 원인부터 보여주되 상세 내용을 확인할 수 있게 한다. 원인 미상일 때 임의의 케이블 불량 등으로 단정하지 않는다.
- 글꼴 누락·줄바꿈·긴 장치명·화면 배율·키보드 포커스·대비를 검사한다. 색 외에 문자·모양으로 상태를 구별한다.
- 성공 효과음과 음성은 분리된 켜기/끄기·음량 후보다. 무음에서도 성공·실패·안전 상태를 알 수 있어야 한다.
- 번역 문자열·실제 상태 코드·표시 조건을 같은 검수표로 관리한다. 영어 전환 후보도 같은 메시지의 뜻을 유지한다.

## 5. 첫 비행과 재시도 — C04~C09

흐름: **연결·보정 확인 → 이륙 → 잠깐 호버 → 전진 → 착륙 → 골대 통과/첫 득점**. 한 번에 한 과제를 보여주며 진행 중 연결/ARM 상태와 안전 안내를 숨기지 않는다.

| 과제 | 안내 초안 | 성공 판정 정의에 필요한 값·증거 |
|---|---|---|
| 이륙 | “천천히 이륙해 봐요.” | 높이 기준·지면 접촉 해제·지속 조건. 텔레포트/초기 배치를 성공으로 세지 않음 |
| 호버 | “잠깐 떠 있어 봐요.” | 높이/위치 허용 구간·유지 시간·이탈 처리. ANGLE을 자동 고도 유지로 설명하지 않음 |
| 전진 | “앞으로 가 봐요.” | LOS에서 이해되는 방향 기준·목표 구간·통과 방향. 기체 전방과 화면 방향 혼동 검토 |
| 착륙 | “천천히 착륙해 봐요.” | 접촉·속도·안정 상태와 DISARM 완료를 구분. 단순 높이만으로 성공 처리하지 않음 |
| 골대 | “골대를 향해 천천히 들어가 봐요.” | 유효 접근 방향·완전 통과·현재 규칙의 득점 자격. 연습 통과와 정규 경기 승인 득점을 구별 |

허용 높이·시간·속도·각도는 첫 측정과 사용자/테스터 검토 후 확정한다. 합의 전에는 “판정 기준 미정”이며 임의 수치를 채워 통과시키지 않는다. 단계 완료 여부와 시각을 기록하고, 연결 손실·리셋·모드 변경 시 과제 상태가 어떻게 바뀌었는지 남긴다.

실패 안내는 “괜찮아요, 다시 해 봐요”와 구체적 원인/다음 행동을 함께 제공한다. 연속 실패 시 설명 보기·이전 단계·종료를 선택할 수 있게 하고 자동 난이도 변경으로 기록 비교 조건을 바꾸지 않는다.

**빠른 재시도:** DISARM 확보 → 이전 시도 결과 확정 → 안전한 시작 위치/각도 복원 → 준비 카운트다운 → 명시적 재개/ARM. 카운트다운만으로 비행하지 않는다. 위치 복원은 명시적인 연습 초기화이며 정상 비행 중 강제 이동과 구분한다.

**결과/기록:** 통과 횟수·최고 연속 성공·완료/중단을 우선 표시한다. 정확도/속도 목표, 기체·배터리·보조·코스·버전이 같은 본인 기록끼리 비교한다. 실패/중단을 성공 분모에서 조용히 빼거나 시뮬레이터 성적을 실기체 자격으로 표시하지 않는다. 훈련 묶음 저장·리플레이는 후속 후보로 남긴다.

## 6. 골대·철망·비행 측정 계획

공통 기록: 커밋/빌드 입력 지문, PC·GPU·드라이버, 장면/시점, 해상도·배율·품질, 기체/배터리/보조, 시드·입력·실행 시간, 전후 영상/로그, 실패·미측정 구간. 변경 요소를 분리하고 동일 조건으로 전후를 비교한다.

### 골대 충돌 — COL-04 / ARN-02/08

1. Practice와 공식 경기 고정 모드를 따로 기준 장면으로 저장한다.
2. 충돌 전 속도·방향·접촉 위치·질량과 최대 변위/각도·반발·정착 시간을 수집한다.
3. 실제 물리 반응이 작은지, 시점/색/배경 때문에 잘 보이지 않는지 분리한다.
4. 감쇠·스프링·회전 제한 변경은 한 번에 구분 가능한 범위로 비교한다. 제한값은 실측/실험 가정을 표시한다.
5. 리셋·반복 충돌·다중 접촉에서 위치·충돌체·득점 영역 정합을 검사한다.

수용: 정한 비교 조건에서 반응이 설명 가능하고 공식 경기 고정 정책·득점 판정·안정성을 깨지 않을 것. 사용자의 “더 분명한 움직임” 만족 여부와 물리 정확도 판단을 별도 기록한다.

### 원거리 철망 — C05 / ARN-11 / GFX-11/12

1. 양 팀 LOS의 가까움/멀리·정면/비스듬한 시점에서 정지 화면과 움직이는 화면을 확보한다.
2. 가는 반투명 선·중복 경계·깊이 충돌·모아레·LOD/재질을 각각 조사 가설로 둔다.
3. TSR은 이미 켜진 기준이다. 활성화 여부만 바꾸는 설명으로 끝내지 않고 설정·재질·기하 차이와 결과를 남긴다.
4. 기체 앞뒤·골대 테두리·중앙선 식별과 평균 FPS 외 느린 프레임도 비교한다.
5. 표시 선을 줄이더라도 네트의 실제 충돌/탈출 방지와 모순되지 않는지 검사한다.

수용: 재현 장면에서 이상 무늬의 개선 근거가 있고 기체/골대 가독성·성능·충돌이 악화되지 않을 것. 재현되지 않은 경우 “해결” 대신 “재현 대기”로 남긴다.

### 비행·프레임 의존성 — CTL-03/10/13

[기존 고정주기 설계](fixed-step-control-design.md)를 재작성하지 않고 따른다. 20/30/45/60/120/240FPS와 100/250ms 지연은 **시험 조건**, 달성 성능이 아니다. 같은 입력에서 자세 오차·호버·정착·소비 전력·실제 제어/solver 간격·완료/보류/생략 시간을 비교한다.

먼저 계측만 추가해 기존 힘을 바꾸지 않는지 확인하고, 단일 힘 경로·상태 전달·수명/리셋·안전 회귀를 검수한 뒤 고정 간격 실험을 판단한다. 렌더 FPS·서브스텝 상한·실제 PID 갱신을 구별한다. 실물 입력 지연과 조종 감각은 별도 현장 검사다.

## 7. 보호 가드·내부 프레임 설계 검토 — C11

이 단계는 모델 편집 전의 설계·권리 검토 계획이다. 현재 디자인의 위법성 또는 특정 특허 등록 사실을 확정하지 않는다.

| 단계 | 산출물·진행 조건 |
|---|---|
| 대상/제약 확인 | 대상 부품 명칭, 길이·외경/원주·조립 공간·모터/배터리 간섭·충돌 형상 제약. 사진으로 실측값을 만들어 내지 않음 |
| 독립 설계안 | 가드와 내부 프레임 각각의 외관·구조 대안, 선택 이유·작성 이력. 기존 외형 복제 여부와 기능 제약을 분리 |
| 권리 검토 준비 | 참조 출처·사용 자산/라이선스·설계 설명·공식 권리 자료를 정리. 전문가에게 질문할 쟁점 명시 |
| 전문가 검토/채택 | 특허 전문가의 검토 범위·판단 조건·미해결 사항 기록. 길이/원주 유지 또는 외관 변경만으로 비침해를 보장하지 않음 |
| 모델 구현 | 채택 후 별도 구현. 원본/내보내기/런타임 메시와 버전 대응 |
| 통합 검수 | 크기·충돌·장식/물리 분리·질량/관성 변경 여부·LOS 식별·렌더 비용과 기존 과제 회귀 |

외부 전문가의 선정·연락·비용 집행은 이 계획 등록만으로 승인되거나 실행된 것이 아니다. 권리 검토가 미해결이면 해당 설계의 채택/배포 판단을 보류하고 다른 독립 작업은 이어갈 수 있다.

### 7-1. 치수·내보내기 인계의 단일 기준

2026-10-28 정적 대조: [가드 생성기](../Scripts/build-cage-geometry.py)는 `Content/Data/cage-geodesic.json`을 생성하고, [내부 기자재 생성기](../Scripts/build-electronics.py)는 조합 메시를 내보낸다. [런타임 기체](../Source/ImperialWingsSimulator/SoccerDronePawn.cpp)는 가드 데이터와 `SM_EquipmentAssembly`를 각각 읽으며 장식 요소의 충돌을 끄고 루트 강체를 별도로 사용한다. **새 그림이나 Blender 파일만 바꾸면 실행본 전체가 바뀐다는 전제로 작업하지 않는다.** 위 경로는 현재 구조 확인이며 이번에 생성·내보내기·게임 실행을 수행하지 않았다.

| 인계 항목 | 반드시 구분할 내용 |
|---|---|
| 치수 원장 | 항목명·단위·기준점/축·값·허용차·출처·확인일·상태. 실측/공식 제한/기존 시뮬레이터 가정/새 설계 제안을 구분하고 미확인 값은 비워 둠 |
| 유지할 길이·원주 | 외곽 최대 치수인지 봉 중심선인지, 어느 단면의 원주인지 먼저 정의. 구가 아닌 새 구조의 전체 치수를 임의의 원 하나로 환산하지 않음 |
| 조립 간섭 | 가드 내부 여유, 프레임·모터 중심/회전축, 프로펠러 회전 범위, 배터리/보드·체결 위치를 같은 좌표계로 대조. 외경 일치만으로 내부 간섭 없음 판정 금지 |
| 원본→런타임 | 생성 스크립트/입력 데이터→원본 모델→내보낸 메시→엔진 자산→참조 경로의 버전 대응. 단위·축·원점·피벗·적용 스케일을 명시하고 중복 스케일 보정 검사 |
| 시각 변경/물리 변경 | 시각안의 외곽·장식과 실제 충돌 구체·질량·무게중심·관성·모터 힘 위치를 별도 변경표로 관리. 메시 외형으로 질량/관성을 자동 추정했다고 주장하지 않음 |

현재 문서의 외경·질량·모터 위치는 기존 모델 설정의 근거이지 새 설계의 확정 치수나 실제 제품 실측표가 아니다. 실제 사용할 값은 위 원장에서 채택한 값으로 일치시키고, 사진 비례 측정으로 빈 값을 채우지 않는다.

**검수 인계:** 가드만 변경 / 내부 프레임만 변경 / 둘을 결합한 상태를 구분해 기준 모델과 비교한다. 각 상태에서 런타임 치수·간섭·LOS 앞뒤 식별·장식 무충돌·참조 자산 로딩을 확인하고, 물리값을 유지한다고 결정했다면 실제 적용값도 유지되는지 확인한다. 물리값을 바꾸는 안은 외형 승인과 별도로 제어·접촉·골대 통과 회귀 검수를 거친다. 허용차와 렌더 비용 한도는 측정 전 임의 확정하지 않는다.

출처/권리 검토 자료에는 치수 원장의 근거와 독립 설계 변경 이력을 연결하되 외부 도면·제품 사진·CAD 원본을 공개 저장소에 복제하지 않는다. 기술 인계가 준비돼도 전문가 검토가 끝났다는 의미는 아니며, 전문가 검토 대상과 실제 채택 모델의 버전이 달라지면 검토 범위를 다시 확인한다.

| 실물 연결·첫 비행 | 실제 장치·안전 설정·사용자 협조 | G4: 축/방향·연속 비행·USB 손실/재개·사용성 관찰. fixture와 별도 결과 | 입력/현장 시험 |
| 싱글/입문 | 입력 준비·과제 성공 조건 확정 | G1~G4: 단계 판정·중단·재시도·결과·동일 조건 비교 | 훈련/UI/QA |
| 시야·골대/제어 | 재현 장면·측정 기준 | 변화별 성능/가독성/물리 회귀, 필요 시 고정주기 실험. 조종 결함 먼저 | 렌더/물리/QA |
| 모델 재설계 | 제약·권리 검토·설계 채택 | 원본/메시/충돌·물리/LOS 대조. 다른 작업과 분리 통합 | 모델/권리 검토/QA |
| 통합 산출물 | 관련 묶음 검수와 미검증 목록 | G5: 실제 빌드 입력→실행본→ZIP→전체 해시→보고서 대응, CI/다른 PC 범위 명시 | 빌드/배포/QA |

### 매 묶음의 출구 조건

- 정상 사용뿐 아니라 취소/뒤로가기·반복 입력·연결 손실·저장 실패·중단 후 재시도를 확인한다.
- 실행마다 새 결과 경로/식별자를 사용하고 예외·비정상 종료·결과 누락 시 과거 성공 파일을 재사용하지 않는다.
- 체크섬 전체 목록과 실제 필수 파일 집합을 대조한다. 누락·변조·중복·경로 이상·검사 제외를 숨기지 않는다.
- CI는 정확한 커밋·실행 ID·검사 범위로 보고한다. CI 통과가 Windows 실제 실행·실물 USB·다른 PC 통과를 대신하지 않는다.
- 허용치가 미정이면 측정 보고까지만 완료할 수 있다. 제품 수용 통과로 표시하려면 기준 확정과 해당 시험 증거가 필요하다.
- 계획 완료 / 구현 완료 / 자동 검사 / 실행 화면 / 실물 입력 / 다른 PC의 상태를 각각 기록한다.
- 실패 원인·복구 또는 되돌릴 기준과 미검증 한계를 남긴 후 통합 여부를 판단한다. 일정은 범위와 현장 시험 가능 시간을 확인한 뒤 추정한다.

## 11. 싱글플레이 메뉴·결과 화면의 상태 계약 — 2026-10-28 후속 상세화

이번 상세화는 **입력 설정 이후 어디로 이동하고, 끝난 시도가 어떤 결과로 남는지**에 집중한다. 2절의 화면 지도와 5절의 첫 비행 과제를 대체하지 않는다. 연결 항목은 SYS-03~09/11, RUL-02/03/16, TRN-01/08/12, DAT-13~15, UX-02/05/10/12/13 및 C04/C06/C08/C13이다. 새 기능 번호·후보 추가나 구현 완료가 아니다.

### 11-1. 화면 상태와 비행 상태를 분리한다

화면 상태, 입력 준비 상태, 기체 ARM 상태, 경기/과제 상태, 저장 상태는 서로 다른 값이다. 예를 들어 “결과 화면”은 “모든 기체가 착륙함”이나 “파일 저장 성공”을 의미하지 않는다. 화면의 한국어 표현은 아래 설계 이름을 사용하되 실제 코드의 클래스·enum 이름을 강제하지 않는다.

| 화면 상태 | 진입 조건·표시 | 허용 동작과 이탈 조건 |
|---|---|---|
| 메인 | 버전/시험판·플레이·조종기 설정·환경설정·종료 | 플레이는 모드 선택으로 이동. 로딩을 중복 시작하지 않음 |
| 싱글 선택 | 자유비행/기초 훈련/코스 연습/경기 연습의 구현 상태 표시 | 사용 가능한 모드만 선택. 미구현은 준비 중·이유 표시 |
| 시작 조건 확인 | 모드·코스·규칙·기체·입력 방식·보조·시작 조건 요약 | 입력이 준비되지 않으면 설정으로 안내. 돌아오면 선택을 보존하되 준비 상태 재검사 |
| 준비/로딩 | 실제 진행 단계·취소 가능 여부 표시 | 취소는 부분 생성된 세션/입력을 정리하고 이전 화면으로. 시간 초과 기준은 측정 후 결정 |
| 비행 준비 | 장면 준비 완료·DISARM·현재 입력 유효성·다음 행동 | 명시적 시작/ARM 절차. 메뉴 선택이나 로딩 완료만으로 ARM 금지 |
| 진행 | 현재 과제/경기·입력·ARM·시간·핵심 경고 | 허용된 설정/메뉴만 접근. 경기 상태와 Practice 보조를 혼합하지 않음 |
| 중단 요청 | 이유·현재 비행 상태·가능한 안전 종료 절차 | 장면/시간 정지와 DISARM을 동일시하지 않음. 확정되지 않은 정책은 11-6에서 결정 |
| 종료 정리 | 과제/경기 결과 고정 여부, 착륙·DISARM 필요 상태, 저장 상태 구분 | 공식 경기 종료 신호만으로 공중 기체를 강제 추락시키지 않고 기존 수동 착륙 계약 유지 |
| 결과 | 완료/중단/판정 대기 및 저장 여부, 해당 시도 요약 | 재시도·모드 선택·메인 이동은 안전한 종료 정리 후 허용 |
| 복구 안내 | 실패한 단계·유지된 설정·다음 행동 | 재시도·이전 화면·종료. 실패를 정상 결과처럼 표시하지 않음 |

**상태 전이 규칙**
- 화면이 닫히거나 이동해도 남은 비행 입력이 다른 화면의 확인/시작으로 처리되지 않게 한다. 선택 연타·Enter/Space 길게 누름을 포함한다.
- 하나의 시작 요청은 하나의 세션만 만든다. 시작 중 다른 요청은 중복 실행하지 않고 진행 중임을 표시한다.
- 취소 뒤 늦게 끝난 로딩/저장 결과가 새 화면·새 시도의 상태를 덮지 않게 세션/작업 식별자를 대조한다.
- 메뉴 복귀·설정 저장·과제 완료 이벤트는 ARM 허가가 아니다. 재진입 시 현재 장치/스로틀/상태를 다시 확인한다.
- 비행 중 앱 전환·입력 상실은 기존 안전 정책을 보존한다. 새로운 일시정지 설계로 기존 입력 손실 처리를 무력화하지 않는다.
- 미구현 멀티 메뉴는 계정 생성·방 접속·온라인 결과 저장을 수행하지 않는다. 10대 장면을 10인 접속으로 표시하지 않는다.

### 11-2. 모드별 결과를 같은 점수로 섞지 않는다

| 모드 | 결과 제목·핵심 내용 | 표시하지 않을 오해 |
|---|---|---|
| 자유비행 | “자유비행을 마쳤어요” 또는 “자유비행을 중단했어요”. 실제 비행 시간·선택 조건, 수집 가능한 항목만 | 과제 없는 비행에 임의의 합격/불합격·승패 부여 |
| 기초 훈련 | 완료 단계/전체 단계, 마지막 진행 단계, 재시도 가능 지점 | 중단 단계를 실패 또는 성공으로 자동 대체 |
| 코스 연습 | 선택 목표(정확도/속도), 유효 통과·시도·최고 연속 성공과 조건 | 보조·기체·코스가 다른 기록의 무조건 순위 비교 |
| 경기 연습 | 규칙 프로필, 팀/세트/점수, 결과 확정 여부, 미구현 판정 범위 | 연습 점수를 공인 경기·협회 인증 결과로 표시 |
| 판정/결과 대기 | “결과 확인이 필요해요”, 보류 이유·확정되지 않은 항목 | 페널티/검토가 남았는데 확정 승패·다음 세트 승수를 표시 |

경기 결과는 승인된 경기 상태에서 가져오고 화면에서 점수·승수를 별도로 계산하지 않는다. RUL-16 전체 결과 확정 절차가 아직 구현되지 않았다면 그 한계를 표시하며 새 UI가 완전한 심판 운영을 제공한다고 주장하지 않는다. 과거 “101개 규칙 검사”는 이 화면의 통과 증거가 아니다.

### 11-3. 결과 화면 구성과 기록 계약

우선순위: **무엇이 끝났는지 → 어떤 결과인지 → 저장됐는지 → 다음에 무엇을 할지**.

- 상단: 모드명·완료/중단/판정 대기. “실패”는 확정된 과제 실패에만 사용하고 프로그램 오류·사용자 취소·연결 손실은 사유를 분리한다.
- 핵심 요약: 모드별 필요한 항목만 표시한다. 빈 값·미수집·계산 불가를 0으로 바꾸지 않는다.
- 조건 요약: 실행 버전·규칙/코스·기체·입력 방식·보조·평가 목표. 상세 설정은 펼쳐 보기로 제공한다.
- 저장 상태: 저장 중 / 저장됨 / 저장 실패 / 저장하지 않음. 화면에 결과가 보이는 것과 디스크 저장을 구분한다.
- 버튼: 같은 조건 다시 연습, 다른 연습 선택, 메인으로. 중단한 단계부터 재개는 상태 복원 검증 전에는 제공하지 않는다.
- 안전 표시: 아직 종료 정리가 필요하면 그 이유와 가능한 행동을 우선 안내한다. 결과 화면이 착륙 조작을 가리거나 의도치 않은 ARM 입력을 받지 않게 한다.

**논리 기록 필드 초안** — 실제 파일 형식/API는 구현 시 확정한다.
- 세션/시도 식별자, 모드, 시작/종료 사유, 규칙/코스/평가 기준 버전.
- 소스·빌드/설정 지문, 기체·배터리·보조·입력 방식의 비교 조건.
- 시각 기준과 유효/누락 구간, 단계별 판정·근거 사건, 확정/미확정 결과.
- 저장 상태·오류, 재시도와 이전 시도의 연결. 개인 원본 보정·하드웨어 고유 식별자를 결과에 불필요하게 포함하지 않는다.

동일 종료 이벤트가 반복되어도 같은 시도를 이중 집계하지 않는다. 재시도는 새 시도이며 이전 실패/중단을 덮지 않는다. 개인 기록 비교는 조건 일치가 확인된 것만 대상으로 하고 불일치 이유를 표시한다. 자동 외부 업로드는 범위에 포함하지 않는다.

### 11-4. 결과 저장·다시하기·종료의 실패 처리

| 상황 | 화면/상태 요구 | 확인할 증거 |
|---|---|---|
| 결과 저장 중 다시하기 연타 | 동일 저장/시작을 중복 생성하지 않음. 저장 작업과 새 시도의 소유 상태 분리 | 세션 ID·파일 수·중복 사건·버튼 상태 |
| 디스크/권한 오류 | 저장 실패를 알리고 가능한 재시도·저장 없이 나가기 선택을 명시 | 실제 오류 코드/안내·이전 기록 보존·새 기록 미완료 표시 |
| 저장 중 종료 | 종료 영향 설명. 취소 시 현재 화면/결과 유지. 강제 종료는 다음 실행에서 불완전 기록 감지 | 부분 파일이 정상 기록으로 읽히지 않는지 |
| 결과 표시 전 프로세스 중단 | 다음 실행에서 존재하는 증거만 복구하고 추정 승패를 만들지 않음 | 불완전/중단 기록, 오래된 성공 결과 재사용 방지 |
| 재시도 초기화 실패 | 기존 결과 보존, 새 시도 시작 실패 표시, 비행 준비/ARM 진행 차단 | 시작 상태·기체 위치·현재 세션·입력 게이트 |
| 조건이 바뀐 재시도 | “같은 조건”이라고 표시하지 않고 변경 항목 확인 | 설정 지문·조건 요약·비교 제외 사유 |
| 과제 완료와 USB 손실 동시 발생 | 시각/사건 순서를 기록하고 정의된 판정 정책 적용 | 입력 손실 안전 동작과 결과 판정이 서로 덮이지 않음 |

완료/중단/연결 손실 사건의 우선순위는 실제 사건 모델에 맞춰 확정한다. 아직 정하지 않은 동시 사건을 도착 순서만으로 확정하거나 결과를 유리하게 선택하지 않는다.

### 11-5. 화면 흐름 수용 시나리오

다음은 앞으로 수행할 기대 결과다. 기존 SC-01~20과 중복되는 안전/판정 시험은 같은 근거를 연결하고 별도 기능 완료 수로 더하지 않는다.

| 흐름 | 기대 결과·관찰점 |
|---|---|
| 메인→싱글→설정 필요→보정 취소→복귀 | 선택 모드 유지, 이전 보정 보존, 준비 완료로 오인하지 않음 |
| 준비 중 뒤로가기→다른 과제 선택→이전 로딩 종료 | 새 과제가 유지되고 취소한 장면/입력/결과가 나타나지 않음 |
| 시작 버튼/확인 키 반복→비행 준비 | 세션 하나, DISARM 유지, 확인 키가 자동 ARM으로 이어지지 않음 |
| 기초 훈련 중 중단→결과→같은 조건 재시도 | 중단 사유 보존, 안전 초기화 후 새 시도, 이전 기록 덮어쓰기 없음 |
| 과제 성공→결과 저장→메인→재실행 | 동일 결과/조건 복원, 중복 집계 없음, ARM 상태 자동 복원 없음 |
| 결과 저장 실패→다시 저장/저장 없이 나가기 | 선택대로 진행하며 저장 실패를 성공으로 표시하지 않음 |
| 경기 종료 시 공중 기체 존재 | 기존 수동 착륙 정책 유지, 종료 화면으로 조작을 강제 차단하지 않음, 새 ARM 제한 |
| 미구현 멀티 클릭·뒤로가기 반복 | 준비 중 안내 후 정상 복귀, 허위 네트워크/대기실 상태 없음 |
| 화면 크기·배율·한국어 긴 문구·키보드만 조작 | 핵심 결과/저장 오류/뒤로가기 접근 가능, 잘림·보이지 않는 포커스 없음 |
| 연결 손실·메뉴 복귀·재시도 복합 | 안전 게이트 유지, 저장/과제/입력 상태별 복구를 구분 |

각 결과에는 실제 실행 종류와 버전·환경·재현 순서·화면/로그를 남긴다. 자동 상태 전이 검사, 실제 화면 조작, 실물 조종기 검사를 각각 판정한다.

### 11-6. 다음 구현을 막는 결정과 진행 가능한 작업

| 먼저 결정할 사항 | 필요한 확인 | 결정 전에도 가능한 작업 |
|---|---|---|
| 오프라인 일시정지의 물리/경기/과제 시간 범위 | 현 시간 계약·안전·경기 모드 정책 대조 | 메뉴 지도·상태 표시·한국어 문구 초안 |
| 공중 상태의 메뉴/결과/종료 흐름 | 기존 수동 착륙과 입력 손실 정책, 실제 UI 가림 검수 | 완료/중단/저장 상태 분리 설계 |
| 동시에 발생한 성공·중단·USB 손실의 판정 | 사건 시각·판정 권한·재현 시나리오 | 사건 기록과 미확정 표시 설계 |
| 저장 실패 후 유지 범위·기록 포맷 호환 | 현재 저장 계층·오류 처리·마이그레이션 검토 | 결과 화면 필드·사용자 선택·테스트 사례 |
| 최초 출시할 싱글 과제 범위 | 기존 구현/판정 가능 항목·현장 검수 시간 | 미구현 상태·메뉴 진입 거부 계약 |

한국어/조종기 최우선 순서는 바뀌지 않는다. 이 절의 후속 구현은 상태 계약 확정→정상 흐름→실패/중단/반복 흐름→실제 화면→실물 입력→산출물 정합 순으로 통합하며, 단계별 근거가 없으면 다음 단계 완료로 표시하지 않는다.

## 12. 한국어 조종기 화면 문구·오류 대응표 — 2026-10-28 후속 상세화

3~4절의 정책을 실제 화면 문구와 오류별 검수로 구체화한다. 아래 한국어는 **제안 문구**이며 현재 공개 실행본에 적용됐다는 뜻이 아니다. 연결 대상은 C01~C03, INP-02~13, CTL-08/14, UX-01/03/05/10/12다.

### 12-1. 기존 동작과 새 문구의 경계

기준 소스 04ff2f4의 [조종기 상태 처리](https://github.com/sun475300-sudo/Drone-Soccer-Simulator/blob/04ff2f441590518455f7a2ae3d7083f22a903387/Source/ImperialWingsSimulator/ImperialRadioSubsystem.cpp)와 [보정 오류 정의](https://github.com/sun475300-sudo/Drone-Soccer-Simulator/blob/04ff2f441590518455f7a2ae3d7083f22a903387/Source/ImperialWingsSimulator/RadioCalibration.cpp)를 정적으로 대조했다.

- **기존 경로:** 장치 선택, Mode 1/2, 안내 보정, 보정 검토/저장/취소, 저장 장치 명시적 연결, 낮은 스로틀 검사, USB 입력 해제, 직접/정밀 스로틀 별도 설정.
- **이번 제안:** 한국어 표시·메시지 우선순위·기본/고급 배치·오류별 복구 버튼·검수 연결. 기존 검사 임계값이나 실제 축을 번역 과정에서 바꾸지 않는다.
- **별도 미구현/보강:** 자유로운 아밍 스위치 배정, 저장 없는 단계 재개, 다중 프로필 이식, 자동 오류 해결. UI 문구를 정했다고 이 기능이 생기지 않는다.
- 기존 보정 중 입력 손실 경로는 이전 저장 프로필을 보존하고 설정 재시작을 안내한다. 특정 단계만 재개하는 기능은 검증 전 약속하지 않는다.
- 기존 코드에 USB 비활성 시 키보드 입력으로 돌아가는 경로가 있다. “USB 사용 안 함”을 “모든 입력 잠금”으로 번역하지 않는다. 실제 ARM/DISARM은 기체 상태를 따로 확인해 표시한다.

### 12-2. 화면별 제목·행동·버튼

주요 문구 한 줄과 도움말/상태줄을 구분한다. 보조 설명이 많으면 펼쳐 보되 안전 거부 이유는 숨기지 않는다. 아래 버튼은 사용 가능한 상태에서만 활성화하며, 미지원 버튼을 동작하는 것처럼 두지 않는다.

| 화면/상태 | 제목·주요 문구 초안 | 버튼 초안 | 보조 표시·조건 |
|---|---|---|---|
| 장치 없음 | 조종기 설정 / “연결된 조종기를 찾지 못했어요.” | 장치 다시 찾기 · 키보드 사용 · 닫기 | USB 데이터 연결/게임 컨트롤러 모드 도움말. 검출 실패만으로 케이블 고장 단정 금지 |
| 장치 목록 | 조종기 선택 / “스틱을 움직여 내 조종기를 확인해 주세요.” | 이 조종기 선택 · 장치 다시 찾기 | 현재 선택·장치명·실제 입력 표시. 같은 이름 장치의 구분 정보는 공개 진단과 분리 |
| 모드 선택 | 스틱 배치 / “사용하는 스틱 배치를 골라 주세요.” | Mode 1 · Mode 2 · 스틱 설정 시작 | 스로틀: Mode 1 오른손 위아래, Mode 2 왼손 위아래. 장치 자체 모드를 프로그램이 바꾼다고 설명하지 않음 |
| 보정 준비 | 스틱 준비 / “스로틀은 내리고, 나머지 스틱은 가운데에 놓아 주세요.” | 이 단계 시작 · 설정 취소 | 선택 모드 그림과 현재 단계. 준비 성공만으로 저장/USB 활성화하지 않음 |
| 축 이동 | 스틱 움직이기 / “그림의 스틱만 양 끝까지 움직여 주세요.” | 움직임 확인 · 설정 취소 | 해당 채널·손 위치 그림, 끝 위치 유지 안내. 실제 보정 알고리즘의 채널 순서를 그대로 사용 |
| 중립 확인 | 스틱 놓기 / “스로틀은 내리고, 나머지 스틱은 가운데에서 멈춰 주세요.” | 중립 확인 · 설정 취소 | 안정성 검사를 통과한 뒤 검토로 이동 |
| 검토 | 설정 확인 / “스틱 배치와 움직이는 방향을 확인해 주세요.” | 확인하고 저장 · 다시 설정 · 설정 취소 | 네 채널의 실제 배정·방향·중립·스로틀 최저. 저장 이전 상태 표시 |
| 저장 성공 | 설정 저장됨 / “설정을 저장했어요. 연결은 따로 진행해 주세요.” | 조종기 연결 · 닫기 | USB 비활성·현재 입력 방식·기체 상태를 별도 표시 |
| 저장된 장치 연결 | 저장한 조종기 / “스로틀을 내린 뒤 연결해 주세요.” | 저장한 조종기 연결 · 장치 선택 | 저장된 장치와 실제 연결 장치가 유일하게 대응할 때만 바로 연결 |
| USB 활성 | 조종기 연결됨 / “입력을 확인한 뒤 비행을 준비해 주세요.” | 입력 확인 · 닫기 | “모터 정지(DISARM)”는 실제 정지 상태일 때만 표시. 연결과 ARM 분리 |
| 고급 설정 | 고급 조종기 설정 / “축과 감도 설정을 직접 조정해요.” | 기본 화면 · 저장/적용 가능한 동작 | 축 번호·반전·데드존과 지원 범위. 보정 중 충돌하는 편집 차단 |
| 스로틀 반응 | 스로틀 반응 / “높이는 스로틀로 직접 조절해요.” | 직접 · 정밀 | 직접/정밀은 선택 곡선이며 고도 유지 아님. 기존 ARM 중 변경 차단·저장 후 재연결 조건 유지 |

**모드별 그림 검수 기준:** Roll은 오른손 좌우, Yaw는 왼손 좌우. Mode 1의 Pitch는 왼손 위아래·Throttle은 오른손 위아래, Mode 2는 그 반대다. 소스의 채널/양의 방향 지시와 그림·한글 문장이 같은 행동을 가리키는지 대조한다. 화면 방향만 보고 축 반전을 자동 결정하지 않는다.

### 12-3. 보정 오류와 한국어 복구 문구

오류 이름은 기존 코드 식별자이며 새 기능 번호가 아니다. 메시지는 실제 오류와 연결한다. 복구 버튼은 필요한 상태 전이를 구현·검수한 경우에만 제공한다.

| 기존 오류 | 주요 문구 초안 | 다음 행동·보존 조건 |
|---|---|---|
| Disconnected | “조종기 입력을 확인할 수 없어요.” | 다시 연결/장치 선택. 보정 중 손실이면 설정 재시작 안내, 이전 저장 보정 보존 |
| InvalidAxis | “사용할 입력 축을 확인해 주세요.” | 고급 축 설정에서 가능한 축 선택. 기본 화면에서는 축 번호보다 스틱 설정 안내 |
| DuplicateAxis | “여러 조작에 같은 입력 축이 선택됐어요.” | 네 채널을 서로 다른 유효 축으로 다시 확인, 자동 중복 허용 금지 |
| UnavailableAxis | “이 조종기에서 선택한 축을 찾을 수 없어요.” | 실제 장치/USB 구성 확인, 다른 장치의 보정을 적용하지 않음 |
| InvalidDeadzone | “데드존 값을 확인해 주세요.” | 현재 검증 코드의 허용 범위를 도움말과 일치시킴. 임계값 변경은 별도 작업 |
| InsufficientSamples | “스틱을 조금 더 움직인 뒤 확인해 주세요.” | 현재 단계의 유효 입력을 충분히 확보. 부적절한 단계에서 자동 진행 금지 |
| InsufficientRange | “스틱을 양 끝까지 충분히 움직여 주세요.” | 장치 출력 범위/실제 움직임 확인. 부족한 범위를 정상 보정으로 저장하지 않음 |
| InvalidCenter | “스로틀을 제외한 스틱을 가운데에 놓아 주세요.” | 실제 중립 재확인. 반전/범위가 잘못됐는지 고급 도움말 제공 |
| ThrottleNotLow | “스로틀을 최저로 내려 주세요.” | 실제 스로틀 축·반전도 확인. 안내만 지우고 연결/ARM을 허용하지 않음 |
| NotCapturing | “먼저 보정 단계를 시작해 주세요.” | 현재 단계로 복귀, 오래된 확인 입력 폐기 |
| MissingRange | “스틱 움직임 범위를 먼저 확인해 주세요.” | 범위 보정 수행. 기존 저장 보정과 미완성 편집 상태 구분 |
| MissingNeutral | “스틱 중립과 최저 스로틀을 확인해 주세요.” | 중립 단계 수행, 범위를 임의 생성하지 않음 |
| NotConfirmed | “보정을 확인하고 저장해 주세요.” | 검토 화면으로 안내, 미확정 프로필 활성화 금지 |
| InvalidSample | “올바르지 않은 입력이 감지됐어요.” | 입력 상태 재확인, 무효 값을 보정에 넣지 않음. 원인 불명은 그대로 표시 |
| AmbiguousMovement | “그림에 표시된 스틱 방향만 움직여 주세요.” | 다른 축의 동시 움직임을 멈추고 단계 재시도 |
| EndpointNotHeld | “마지막 끝 위치에서 스틱을 멈춘 뒤 확인해 주세요.” | 실제 끝 위치/유지 검사, 고정 대기시간을 UI만으로 추정하지 않음 |
| InputNotStable | “스틱을 잠시 멈춘 뒤 다시 확인해 주세요.” | 안정성 검사를 유지. 드리프트를 사용자 실수로 단정하지 않음 |
| IncompleteSweep | “가운데에서 시작해 양쪽 끝까지 움직여 주세요.” | 해당 단계의 재시작 조건 확인. 한쪽 움직임만으로 완료 금지 |
| InvalidStickMode | “Mode 1 또는 Mode 2를 선택해 주세요.” | 실제 배치 선택 후 재보정, 저장된 다른 모드와 혼합 금지 |
| 알 수 없는 오류 | “설정을 완료하지 못했어요.” | 상세 진단 확인·취소/재시도. 추정 원인을 사실처럼 출력하지 않음 |

### 12-4. 연결·저장 실패 메시지

| 실제 분기/상태 | 주요 문구 초안 | 복구 동작의 제한 |
|---|---|---|
| 저장 프로필 없음 | “저장된 조종기 설정이 없어요.” | 장치 선택→스틱 설정으로 안내. USB 활성화 안 함 |
| 저장 장치가 유일하지 않음 | “연결할 조종기를 직접 선택해 주세요.” | 여러 후보 중 임의 선택 금지. 연결 가능 여부를 선택 후 다시 검사 |
| 선택 모드와 저장 모드 불일치 | “선택한 스틱 배치와 저장된 설정이 달라요.” | 저장된 배치 선택 또는 실제 배치 재보정. 이전 설정 유지 |
| 장치 식별 변경 | “조종기 구성이 바뀌었어요. 장치를 다시 확인해 주세요.” | 이름이 같아도 확인 없이 이전 프로필 활성화하지 않음 |
| 읽기 실패/입력 시간 초과 | “입력이 끊겨 조종기 사용을 멈췄어요.” | USB 비활성·현재 입력 방식·기체 실제 상태 구분. 명시적 재연결 요구 |
| 보정 중 입력 손실 | “연결이 끊겨 스틱 설정을 중단했어요.” | “이전 저장 설정은 유지돼요”는 실제 보존 확인 상태에 연결. 재연결 후 설정 재시작 |
| 프로필 저장 실패 | “설정을 저장하지 못했어요.” | 디스크/권한 등 확인된 원인만 상세 표시. 저장됨/연결 가능 상태로 거짓 전환 금지 |
| 정밀 스로틀 저장 실패 | “스로틀 반응을 저장하지 못했어요. 이전 설정을 유지해요.” | 기존 선택이 실제 유지됐는지 확인, USB 보정 파일과 별개로 처리 |
| 정밀 스로틀 파일 손상/미지원 | “저장된 스로틀 설정을 읽지 못해 직접 모드를 사용해요.” | 현재 소스의 DIRECT 대체 경로와 일치. “조종기 보정 초기화”라고 잘못 안내하지 않음 |
| 보정 중 설정 변경 요청 | “보정을 마치거나 취소한 뒤 변경해 주세요.” | 모드/곡선/축 편집의 차단 조건과 일치 |
| ARM 중 곡선 변경 요청 | “수동 조종 기체를 모두 모터 정지한 뒤 변경해 주세요.” | 다른 기체의 ARM 상태까지 기존 검사대로 확인 |
| 진단 내보내기 실패 | “진단 파일을 저장하지 못했어요.” | 입력/보정 결과와 분리. 생성 실패를 전송 실패로 표현하지 않음 |

### 12-5. 문구 노출·검수 규칙

- **고정 상태줄:** 현재 장치, Mode 1/2, 실제 입력 방식, USB 활성 여부, 저장 상태, 기체 ARM/DISARM을 구별한다. 장치 검출만으로 “비행 준비 완료”를 표시하지 않는다.
- **메시지 우선순위 제안:** 입력 손실/안전 거부 → 진행을 막는 보정·저장 오류 → 필요한 다음 행동 → 성공 알림. 최신 원인과 해소 상태를 연결하고 오래된 성공 메시지로 현재 오류를 덮지 않는다.
- 오류 반복마다 팝업을 쌓거나 버튼 포커스를 빼앗지 않는다. 오류가 해소되어도 명시적 확인이 필요한 연결/ARM 단계를 건너뛰지 않는다.
- 숫자·단위·기종명은 번역 문자열에 고정하지 않고 실제 검증/선택 상태와 맞춘다. 장치명이 비거나 길어도 버튼/안전 문구를 밀어내지 않게 검사한다.
- 축·중립 시각화는 실제 표본에 근거하고 stale 입력을 현재 움직임처럼 그리지 않는다. 시각화 프레임 수를 실제 입력 지연 측정값으로 쓰지 않는다.
- 진단에는 오류 식별자·발생 단계·버전·시각·선택 모드를 남기는 방안을 검토한다. 개인 프로필·고유 장치 식별자를 사용자 동의 없이 공개 저장소로 보내지 않는다.

| 검수 시나리오 | 수용 기준·증거 |
|---|---|
| 장치 없음→연결→검색→선택 | 검출/선택/USB 활성/ARM이 각각 구별되고 문구가 실제 상태에 맞음 |
| 두 장치·같은 이름·저장 후보 다수 | 임의 장치 연결 없음, 직접 선택 안내와 실제 입력 대조 |
| Mode 1/2 전환→취소→재선택 | 그림/채널/스로틀 위치 일치, 이전 저장 보정 보존, 다른 모드 활성화 차단 |
| 한쪽만 이동·두 축 동시·끝 미유지·중립 흔들림 | 해당 오류 문구와 다음 행동이 각각 맞고 잘못된 완료 없음 |
| 낮지 않은 스로틀에서 저장/연결/ARM 요청 | 서로 다른 실제 거부 지점을 구분, 문구 표시 후 안전 조건 우회 없음 |
| 보정 중 USB 분리→재연결 | 중단·저장 보존·설정 재시작 안내, 자동 완료/연결/ARM 없음 |
| 무효/손상 프로필·정밀 스로틀 설정 손상 | 두 파일의 실패와 복구 상태가 섞이지 않고 실제 대체 상태 표시 |
| 저장 권한 오류·반복 저장·취소 직후 늦은 결과 | 실패/취소 상태 정확, 이전 정상 값 유지, 성공 문구 잔존/중복 저장 없음 |
| 키보드 사용 선택·설정창 닫기·포커스 이동 | USB 비활성과 키보드 사용 구분, 닫기 키가 ARM 입력으로 전달되지 않음 |
| 긴 한국어/장치명·배율 변경·키보드만 조작 | 오류와 해결 버튼 읽기/접근 가능, 숨은 포커스·잘림·잘못된 줄바꿈 없음 |

정적 오류 대응표 검수 → fixture 오류 분기 검사 → 실제 화면 표시/버튼 검사 → 실물 장치 조작 순서로 증거를 분리한다. 이 표를 작성한 것만으로 한국어 적용·오류 재현·실물 조종 검수를 통과한 것이 아니다.

## 13. 첫 사용자 현장 검수 절차 — 한국어·간편 설정의 실제 사용성

다음 우선 검수는 **개발자가 설명해 주지 않아도 처음 사용하는 사람이 설정과 첫 비행을 진행할 수 있는가**다. 12절의 문구 대응과 자동 오류 검사는 필요하지만 이 질문에 대신 답하지 못한다. 이 절은 C01~C04, INP-05/06/12/13, QA-03/04/08/12, UX-01/05/12에 연결되는 시험 계획이며 새 기능 또는 실행 결과가 아니다.

### 13-1. 시험 종류와 역할

| 종류 | 목적 | 완료로 볼 수 없는 것 |
|---|---|---|
| 개발자 사전 점검 | 실제 시험본·설정 보존·입력 안전·오류/복구 경로 확인 | 초보자 독립 설정 성공 |
| 첫 사용자 관찰 | 설명서/화면으로 장치 선택→보정→첫 비행까지 가능한지 관찰 | 모든 조종기 호환 또는 실기체 비행 능력 |
| 동일 사용자 재접속 | 저장한 보정으로 다음 실행·연결 복구가 이해되는지 확인 | 새 사용자 최초 설정 검수의 대체 |
| 다른 PC 검수 | 설치·글꼴·드라이버·장치·화면 배율의 환경 차이 확인 | 같은 PC의 새 폴더 실행만으로 충족 |

역할은 **조작자 / 관찰자 / 결과 정리 담당**으로 구분한다. 한 사람이 여러 역할을 맡을 수 있으나 개발자가 직접 조작한 결과를 첫 사용자 독립 성공으로 기록하지 않는다. 실제 참여자·일정은 아직 정하지 않았다. 사용자의 친구에게 연락하거나 참여를 요청한 것은 아니다.

### 13-2. 현장 시험 전 준비·중단 조건

- 실행본의 버전·입력 지문·검사 대상 커밋을 확인한다. 기획 문서만 갱신된 상태에서는 새 UI를 현장 시험했다고 기록하지 않는다.
- 기존 개인 보정을 보존한다. 최초 설정 시험은 동의한 별도 사용자 데이터/시험 프로필에서 진행하며 기존 정상 프로필을 무단 삭제하지 않는다.
- 조종기 기종·펌웨어/모델 설정·USB 모드·케이블/허브 구성·Mode 1/2·PC/GPU/화면 배율을 필요한 범위만 기록한다. 고유 식별자·개인 파일 전체 공개는 필요하지 않다.
- 조종기는 시뮬레이터 입력에만 사용한다. 실제 비행체나 모터에 명령을 보내는 시험은 범위 밖이다. 실기체 연결이 의심되면 중단하고 분리 여부를 확인한다.
- 시작 상태는 선택 장치·입력 유효성·스로틀 최저·기체 DISARM을 실제 화면/로그에서 확인한다. USB 활성 표시만으로 안전 상태를 추정하지 않는다.
- 의도치 않은 ARM, 엉뚱한 기체/축 조작, 기존 설정 손실, 입력 손실 뒤 예기치 않은 재개가 발생하면 해당 비행 시험을 중단하고 근거를 보존한다. 원인 확인 전 같은 위험 동작을 반복하지 않는다.
- USB 분리 시험은 정상 준비/비행 경로를 확인하고 중단·복구 수단을 이해한 뒤 별도로 수행한다. 기체가 공중인지·메뉴인지 등 시험 상태를 기록한다.
- 녹화·스크린샷·입력 기록은 목적과 보관 범위를 설명하고 참여자 동의를 받는다. 카메라/마이크 수집은 자동 필수 조건이 아니다.

### 13-3. 조작자에게 줄 과제와 관찰 기록

처음에는 목표만 설명하고 클릭 순서나 정답 축을 대신 알려주지 않는다. 사용 가능한 화면 도움말·문서는 열어 볼 수 있다. 안전상 개입이 필요하면 즉시 개입하고 그 시도는 독립 성공과 구분한다.

| 과제 | 조작자에게 줄 말의 초안 | 관찰할 항목 |
|---|---|---|
| 시작·선택 | “프로그램에서 본인 조종기를 선택해 주세요.” | 어떤 메뉴를 먼저 찾는지, 장치명이 비슷할 때 실제 입력으로 확인하는지 |
| 배치·보정 | “평소 사용하는 스틱 배치로 설정해 주세요.” | Mode 의미 이해, 손 위치 그림, 한 축씩 움직임, 오류 후 다음 행동 |
| 저장·준비 | “설정을 저장하고 비행을 준비해 주세요.” | 저장/연결/ARM을 혼동하는지, 현재 입력 방식·스로틀 조건을 읽는지 |
| 첫 과제 | “화면 안내에 따라 첫 비행 과제를 진행해 주세요.” | 한 줄 안내의 이해, 앞뒤 방향 식별, 성공/중단 이유와 다음 단계 이해 |
| 실패 후 복구 | “방금 실패한 연습을 다시 시작해 주세요.” | 결과 보존, 같은 조건 여부, 재시도 위치·DISARM·명시적 재개 이해 |
| 다음 실행 | “프로그램을 다시 열고 저장한 설정으로 연결해 주세요.” | 기존 모드/보정 유지, 불필요한 재보정 유도, 자동 활성/ARM 여부 |
| 연결 장애 | “연결 상태를 확인하고 화면 안내대로 복구해 주세요.” | USB 손실 사유, 키보드/USB 구분, 재연결 후 재확인·재개 절차 |

과제 사이에 “이 버튼을 누르면 된다”는 설명을 추가했다면 도움의 시각·내용·이유를 기록한다. 도움 이후 성공은 유효한 복구 관찰이지만 도움 없는 최초 성공으로 바꾸지 않는다. 반복 학습으로 좋아진 결과와 처음 보는 사람의 결과를 섞지 않는다.

### 13-4. 관찰 지표와 판정 방식

| 기록 항목 | 정의·주의 |
|---|---|
| 과제 결과 | 독립 완료 / 도움 후 완료 / 미완료 / 안전 중단 / 환경상 미실행. 자동 기능 시험의 통과/실패와 별도 축 |
| 소요 구간 | 시작·사용자 조작·프로그램 대기·연결 장애·도움 제공 구간을 분리. 중단을 빠른 완료로 세지 않음 |
| 되돌아감 | 이전 단계/재보정을 선택한 지점과 이유. 횟수만으로 사용자 능력을 평가하지 않음 |
| 오류 이해 | 오류 문구를 본 뒤 실제로 취한 행동, 같은 원인 반복 여부, 안내가 실제 원인과 맞았는지 |
| 안전 상태 이해 | 연결·저장·ARM 차이를 설명하거나 행동으로 구별할 수 있는지. 설문 답변과 실제 동작을 분리 |
| 설정 보존 | 시험 전후·재실행 후 모드/축/보정 상태 대조. 공개 자료에는 개인 원본 보정 대신 필요한 비식별 결과만 |
| 환경 한계 | 장치 배터리/케이블/드라이버/글꼴 등 중단 요인과 시험 가능 범위. 미실행을 실패 또는 통과로 바꾸지 않음 |

합격 시간·참여자 수·성공률 목표는 아직 정하지 않았다. 최초 관찰에서 병목을 찾고 지원 대상·반복 가능한 조건과 함께 수용 기준을 확정한다. 한 사람의 만족을 전체 사용자 검증으로 일반화하지 않는다.

### 13-5. 발견 사항의 수정 우선순위와 재검수

1. **진행 중단 결함:** 의도치 않은 ARM/입력, 설정 손실, 실제 상태와 반대인 안전 안내. 원인·복구·관련 회귀 확인 전 해당 흐름의 수용을 보류한다.
2. **과제 차단:** 장치/모드 선택 불가, 문구 잘림으로 다음 행동 불명, 저장 실패 원인 미표시. 해당 화면과 연결된 이전/다음 단계까지 재검수한다.
3. **도움 의존:** 그림/용어 혼동, 반복 재보정, 연결과 ARM 혼동. 문구·배치 변경 전후를 같은 과제로 비교하고 학습 효과를 구분한다.
4. **편의 보강:** 클릭 수·표시 순서·부가 도움말. 안전·과제 차단 해결 뒤 검토하며 관찰 없는 취향 변경과 구별한다.

결과 정리는 “어려웠다” 한 줄 대신 **과제 → 관찰된 행동 → 화면/상태 → 원인 가설 → 변경안 → 재검수 결과**로 남긴다. 사용자 발언과 개발자의 해석을 분리하고 발언을 동의 없이 공개 식별 정보와 함께 게시하지 않는다.

**출구 조건:** 시험본 출처와 참여/환경 범위, 과제별 독립/도움/미실행 결과, 안전·설정 보존 증거, 수정 후 재검수와 남은 제한을 갖춰야 현장 검수 범위를 보고할 수 있다. 이 조건 충족 전에는 “한국어가 적용됐다” 또는 “설정 화면이 생겼다”만으로 간편 설정 사용성 검증 완료라고 표시하지 않는다.

## 14. 골대·철망 문제의 비교 실험 카드와 판정 절차

6절은 측정할 항목을 정의했다. 이 절은 **어떤 순서로 비교하고, 어떤 증거에서 다음 조치를 선택할지**를 구체화한다. 연결은 COL-04, ARN-02/08/11, GFX-11/12, PERF-07/10, QA-02/12다. 아래 실험 이름은 시험 구분용이며 기능/후보 번호를 늘리지 않는다. 원인 확정·개선 구현·실행 시험은 아직 하지 않았다.

### 14-1. 먼저 기준 장면을 고정한다

하나의 재현 카드에 실행본/소스 지문, 모드, 기체·질량·배터리, 입력 또는 fixture, 초기 위치/속도, 카메라 위치/시선/줌, 해상도·배율·내부 렌더 비율·품질·TSR 설정, PC/GPU·예열 상태를 기록한다. 기록할 수 없는 값은 공란 대신 미확인으로 표시한다.

- 사용자 실제 조종 재현과 초기 조건을 지정한 자동 fixture를 구별한다. fixture로 증상이 보이면 재현 근거는 되지만 실제 조종감 검증이 되지는 않는다.
- 기준 A와 후보 B는 같은 조건에서 비교하며 바꾼 항목을 명시한다. 물리·재질·카메라를 동시에 바꾼 결과로 하나의 원인을 확정하지 않는다.
- 정지 이미지뿐 아니라 움직이는 장면을 확보한다. 영상 재압축/화면 축소로 생긴 무늬와 실제 게임 화면의 문제를 구분하기 위해 원본 해상도·캡처 조건을 남긴다.
- 실행 순서·예열·프레임 편차를 기록하고 기준 장면을 다시 실행해 일회성 결과인지 확인한다. 반복 횟수와 측정 시간은 장면 비용·변동을 확인한 뒤 정하며 아직 보장 수치로 쓰지 않는다.

### 14-2. 골대: 반응 자체와 보이는 정도를 나눠 비교한다

사용자 요구는 “충돌했을 때 움직임이 둔하게 느껴져 반응을 더 분명하게 보고 싶다”다. 비접촉 상태의 자발적인 움직임 신고로 바꾸지 않는다.

| 실험 카드 | 고정/변경할 것 | 얻으려는 근거·다음 판단 |
|---|---|---|
| 비접촉 기준 | 모드·카메라·기체 배치 고정, 충돌 없음 | 골대 기준 위치/자세와 자연 변동 기록. 접촉 전부터 흔들리면 충돌 개선 실험과 분리 조사 |
| 같은 충돌 재현 | Practice, 같은 접촉 위치·진입 방향·속도·기체 조건 | 실제 최대 변위/각도·복원 추이와 영상의 반응 인지 비교 |
| 시각만 비교 | 물리 계수/충돌 입력 고정, 카메라 또는 배경/표시 하나만 변경 | 수치 반응은 같은데 인지만 달라지는지 확인. 시각 개선을 물리 정확도 향상으로 보고하지 않음 |
| 물리만 비교 | 카메라/재질 고정, 스프링·감쇠·제한 등 검토 대상 하나 변경 | 최대 반응·정착·반발·안정성 변화. 계수 변경 근거와 가정/실측 여부 기록 |
| 접촉 위치/방향 비교 | 선택 계수 고정, 서로 다른 접촉 조건을 별도 카드로 실행 | 특정 방향만 과장되거나 중심/테두리 반응이 불연속인지 확인 |
| 공식 경기 회귀 | 공식 경기 고정 정책과 같은 접촉 조건 | Practice 개선이 공식 경기 골대 고정을 풀지 않았는지 확인 |
| 초기화·연속 접촉 | reset 전후와 반복/다중 접촉을 별도 실행 | 잔류 위치/속도·과도한 진동·득점 영역 불일치·반발 누적 확인 |

최대 변위/각도는 접촉 직전 기준 자세에 대한 값으로 정의한다. 정착 시간은 사전에 합의할 허용 구간에 들어간 뒤 유지하는 조건까지 정해야 하며, 화면상 멈춰 보였다는 이유만으로 수치를 확정하지 않는다. 득점 영역은 실제 골대 좌표계와 함께 대조한다.

**다음 조치:** 수치 반응은 충분하나 잘 안 보이면 시각 조정을 먼저 검토한다. 실제 반응이 작다면 계수/제약/충격 전달 경로를 조사하되 “더 크게 흔들림”만을 통과 기준으로 삼지 않는다. 기체 관통·반발 폭주·정착 실패·공식 경기 고정 해제·득점 불일치가 생긴 후보는 채택하지 않고 원인을 기록한다.

### 14-3. 철망: 원인별 분리 실험

거리·정면/비스듬한 시점·정지/이동·양 팀 LOS의 대표 재현 카드를 먼저 고른다. “가깝다/멀다”만 적지 말고 카메라와 대상 위치를 저장한다. TSR은 이미 켜진 기준이므로 새 활성화 자체를 수정 성과로 쓰지 않는다.

| 조사 가설 | 비교 방법의 제안 | 그 결과로 단정할 수 없는 것 |
|---|---|---|
| 경계에 선/메시 중복 | 진단용 표시에서 의심 경계만 분리·숨김 비교, 생성 개수/위치 확인 | 숨겼더니 좋아졌다는 이유만으로 모든 경계가 중복이라고 결론 |
| 깊이가 겹친 면/선 | 의심 요소를 구별해 표시하고 같은 시점의 깊이 관계 조사 | 무조건 z-fighting으로 확정하거나 임의 위치 이동을 최종 수정으로 채택 |
| 가는 선의 공간 앨리어싱/모아레 | 기하 고정, 내부 해상도/선 표시 방식을 각각 비교 | 해상도 증가 결과를 다른 PC에서도 가능한 성능 해결로 보장 |
| 반투명 재질/시간적 잔상 | 기하·카메라 고정, 진단용 재질 비교 및 정지→카메라 이동→정지 관찰 | 재질 변경으로 사라진 현상을 물리 네트 오류라고 판단 |
| 거리 전환/LOD | 시점 경로를 고정하고 전환 전후의 선 수·밝기·가림 기록 | LOD가 현재 구현돼 있다고 추정하거나 전환 거리 임의 확정 |
| 캡처/축소 문제 | 실제 게임 화면·원본 캡처·공유용 축소본 대조 | 공유 영상에만 보이는 무늬를 게임 런타임 결함으로 확정 |

분리 표시·재질 대체·진단 토글은 **후속 실험 제안**이다. 이번 문서 작업에서 그런 기능을 구현하거나 네트를 제거한 것이 아니다. 진단용 숨김을 제품 해결책으로 남기지 않으며 실제 충돌/탈출 방지는 보존한다.

### 14-4. 결과를 채택/보류하는 기준

| 판정 | 필요한 근거 | 다음 행동 |
|---|---|---|
| 재현 대기 | 증상 장면·조건이 없거나 동일 조건에서 확인되지 않음 | 사용자 장면/환경 확인 또는 관찰 범위 확대. 해결됐다고 표시하지 않음 |
| 재현 확인·원인 미확정 | 같은 조건의 증상 증거는 있으나 분리 실험이 부족 | 가설별 비교. 근거 없는 원인 이름을 결함 제목에 확정하지 않음 |
| 개선 후보 | 기준 대비 증상이 줄었으나 안전/가독성/성능 회귀 일부 미실행 | 남은 회귀와 조건별 확인, 채택 보류 사유 명시 |
| 채택 가능 | 합의된 수용 기준과 필요한 회귀 증거 확보 | 적용 범위·한계·설정·실행본 출처를 기록하고 통합 판단 |
| 회귀 발생 | 기체/골대 식별 저하, 충돌/득점 변화, 목표 성능 미달 등 | 후보를 보류·되돌리고 실패 장면 보존 |

철망 개선은 이상 무늬 감소와 함께 **기체 앞뒤·골대 테두리·중앙선 식별**, 평균 외 느린 프레임, 충돌 모델 불변/의도된 변경 여부를 확인한다. 골대 개선은 가시성과 함께 물리 안정성·모드 정책·득점 정합을 확인한다. “보기 좋아졌다”는 관찰과 측정 결과를 각각 남긴다.

수용할 변위/정착·식별 성공·프레임 비용의 허용치는 현재 미정이다. 실제 기준 측정과 지원 환경·사용자 우선순위에 맞춰 확정하며, 기준 미정 상태에서는 개선 비교까지만 보고한다. 정적 코드 검토, 진단 fixture, 실제 화면, 사용자 조종 평가를 하나의 통과 결과로 합치지 않는다.

**실험 카드 결과 필드:** 증상·가설 / 기준 A와 후보 B의 정확한 차이 / 고정 조건 / 실제 관찰·측정값 / 재현·반복 범위 / 회귀 결과 / 미확인·판정 / 채택 또는 보류 이유 / 커밋·빌드·로그·원본 화면 경로. 개인 경로와 장치 식별자는 공개 전 필요한 범위로 줄인다.

## 15. 싱글플레이 포지션별 연습 — 사용자 요청 반영

사용자 요청: **“포지션별 연습 하는 싱글플레이도 있었으면 좋겠어.”** 한국어·간편 조종기 설정 우선순위는 유지하며, 연결/첫 비행 이후 선택할 훈련으로 구체화한다. 기존 C09/C14/C15 및 TRN-05~09/12/14/16, AI-07~10, TEAM-01/10에 연결한다. 기능 326개·후보 16개를 늘리지 않는다.

### 15-1. 기존 기반과 추가할 범위

최신 원격의 [배치 코드](../Source/ImperialWingsSimulator/ImperialSoccerLayout.h)에는 STRIKER/GUIDE/LIBERO/SWEEPER/KEEPER 역할 이름·색·출발/LOS 위치가 있고, [HUD](../Source/ImperialWingsSimulator/ImperialHUD.cpp)는 선택 기체 역할과 AUTO FLEET/HOLD/RETURN을 표시한다. 이는 **역할별 과제·난이도·수용 판정·결과 화면이 구현됐다는 근거가 아니다**. 기존 기능 명세는 역할 훈련과 전술 상대를 후속으로 관리한다.

이 절에서 역할명은 현재 프로젝트의 선택 항목을 식별하기 위한 것이다. 실제 협회/대회의 포지션 정의·역할 수행 의무를 새로 확정하지 않으며, 아래 공격·수비 과제는 **제품 훈련 예시**다. 역할별 과제 배정과 한국어 명칭은 사용자/현장 코치 검토 후 확정한다.

### 15-2. 진입부터 결과까지

**메인 → 플레이 → 싱글플레이 → 포지션별 연습 → 역할/훈련 목표 선택 → 과제 설명·조건 확인 → 비행 준비 → 수동 연습 → 결과·같은 조건 재시도.**

- 역할 카드에는 현재 이름·색뿐 아니라 텍스트/기호, “무엇을 연습하는지”, 구현/준비 중 상태를 표시한다.
- 역할과 목표를 분리한다. 공격 접근·지원 이동·수비 위치 등 목표를 보여주고 특정 역할은 한 행동만 해야 한다고 가르치지 않는다.
- 과제 설명은 “목표”, “성공 조건”, “주의할 점”, “실패/중단 후 재시도”를 짧게 제공한다. 규칙에 따른 판정과 자체 훈련 목표를 나란히 구분한다.
- 선택한 기체·팀·LOS 시점·시작 조건을 확인한다. 다른 역할 선택이 저장한 조종기 보정을 바꾸지 않는다.
- 사용자 조종은 수동으로 유지한다. 경로선·방향 보조는 선택/사용 여부를 표시하며 자동 APF로 사용자 과제를 대신 수행해 성공 처리하지 않는다.
- 진행/중단/결과/저장/재시도는 11절의 공통 상태 계약을 재사용한다. 역할 연습만의 별도 자동 ARM 또는 저장 예외를 만들지 않는다.

### 15-3. 공격·지원·수비 과제 예시

아래 표는 설계 후보다. 목표 구간의 좌표·속도·허용 오차·유지 시간은 미정이며 시험 가능한 규칙/장면을 만든 뒤 확정한다.

| 훈련 목표 예시 | 사용자 행동과 과제 흐름 | 결과로 관찰할 것 | 해석 제한 |
|---|---|---|---|
| 공격 접근·통과 | 지정 시작점→접근 구간→올바른 방향 정렬→골대 완전 통과→복귀 지점 | 구간 순서·진입 방향·접촉·유효 통과·복귀 완료 | 연습 통과와 실제 경기 득점 자격을 구분. 가장 빠른 접근이 최적 전술이라는 뜻 아님 |
| 공격 재접근 | 실패한 접근 위치/각도에서 시작→골대와 거리 확보→다시 정렬→재시도 | 회복 과정·새 접근의 통과 여부·불필요 접촉 | 초기화로 이동한 거리를 조종 성과로 세지 않음 |
| 지원 이동·간격 | 표시된 동료 기준 위치 또는 비충돌 경로를 보고 지정 지원 구간으로 이동→유지→복귀 | 목표 구간 체류·동선·간격·접촉 사건 | 위치/접촉 횟수만으로 동료 지원 효과를 확정하지 않음 |
| 수비 위치 유지 | 자기 골대 주변의 지정 구간으로 이동→시야/방향을 유지→변경된 목표 구간으로 전환 | 위치 오차·방향·구간 이탈·기체/골대 접촉 | 실제 수비 성공/실점 방지와 구별되는 기초 과제 |
| 수비 이동·차단 준비 | 표시된 접근 경로를 보고 대응 구간으로 이동→안전하게 위치 조정→복귀 | 이동 시작·도착·구간 점유와 상대 경로의 관계 | 표시선 대응만으로 실제 상대 차단에 성공했다고 표시하지 않음 |
| 공격/수비 후 복귀 | 지정 사건/신호 뒤 복귀 구간 도달→다음 과제 준비 | 사건부터 복귀까지의 시간과 경로·완료 여부 | 경기 오프사이드 해제 등 규정 판정은 별도 검증 없이는 대신하지 않음 |

초기 화면에서는 “공격 접근”, “지원 이동”, “수비 위치”처럼 과제 목적을 우선 설명하고 기존 역할명과 연결한다. STRIKER에 공격 과제를, 나머지 역할에 어떤 지원/수비 과제를 연결할지는 예시 배정안을 검토하되 공식 정의처럼 고정하지 않는다.

### 15-4. 첫 제공 범위와 후속 후보

| 구분 | 범위·선행 조건 |
|---|---|
| MVP 제안 | 사용자 1명·수동 기체 1대 중심, 고정된 시작/목표 구간, 공격 접근·수비 위치 기초 과제부터. 기존 골대 판정·입력·LOS 기반을 재사용하되 과제 판정은 별도 구현/검수 |
| MVP에서 제외 | 적응형 전술 AI·완전한 팀 전략 평가·실시간 멀티·공인 자격 점수·자동 역할 승계/심판 운영 |
| 다음 단계 | 지원 이동/복귀 묶음, 정해진 경로의 움직이는 기준 대상, 조건 저장·본인 기록 비교 |
| 물리 상대 후속 | 실제 힘 기반 상대의 공격/수비·반응 한계·난이도·통신 장애 처리 검증 후 제공. 기존 APF 이동을 전술 상대 완성으로 표시하지 않음 |
| 심화 후보 | 역할 교대·불리한 인원/점수 상황·팀 전술 중단/설명·리플레이 복기. 규정·논리 상태·데이터 의존성을 먼저 해결 |

비충돌 기준 대상은 화면 안내/고스트이며 접촉·득점에 참여하지 않는다고 표시한다. 실제 물리 상대와 같은 모습으로 혼동시키지 않는다. 기존 10대 배치를 그대로 두는 경우 선택하지 않은 기체의 제어/충돌 상태를 과제 조건에 명시하고 의도치 않게 움직이지 않는지 검사한다.

### 15-5. 난이도와 결과

- 난이도는 이름만 “쉬움/어려움”으로 나누지 않고 시작 거리/각도·목표 구간·유지 조건·보조 표시·상대 유무처럼 **실제로 바뀌는 조건**을 보여준다.
- 최초 단계는 고정 조건에서 사용법을 익히게 하고, 조건 다양화·움직이는 상대·복합 과제는 순차 검토한다. 처음부터 입력 감도나 물리를 몰래 바꾸지 않는다.
- 과제별 성공 판정/실패 사유와 중단/미실행을 구분한다. 공격은 유효 통과·접근/복귀, 수비는 위치/방향 유지처럼 측정 가능한 항목을 우선한다.
- 성공률에는 유효 시도 분모와 제외/미완료를 표시한다. 수비 시도 정의가 없으면 “수비 성공률” 대신 관찰한 위치 유지/구간 도달만 보여준다.
- 점수 하나로 역할 능력을 단정하지 않는다. 종합점수·등급·가중치는 근거/판정 기준 확정 전 제공하지 않는다.
- 같은 역할이라도 과제·버전·기체·보조·난이도 조건이 다르면 기록을 직접 순위 비교하지 않는다. 시간 비교는 사용한 시계와 중단 구간 정책을 명시한다.
- 안내 예: “골대는 통과했지만 복귀 단계는 아직 끝나지 않았어요”, “목표 구간에 도착했어요”, “연결이 끊겨 연습을 중단했어요”. 실제 판정과 맞을 때만 표시한다.

### 15-6. 판정·실패 복구·테스트

과제의 준비→진행→완료/실패/중단 전이는 경기 상태와 분리한다. 훈련 목표를 달성했다고 경기 점수를 임의 변경하거나 정규 경기에서 자율 보조를 허용하지 않는다. 부분 통과·역방향·테두리 접촉·복귀 누락은 각각 사건으로 남긴다.

재시도는 현재 기체/상대의 안전 상태를 확보한 뒤 이전 결과를 보존하고 새 시도를 만든다. 시작 위치/각도 복원은 명시적인 초기화다. 진행 중 편의상 순간이동으로 목표 구간에 넣지 않는다. USB/포커스 손실·과제 취소·저장 실패는 공통 복구 계약을 따르고 자동 ARM하지 않는다.

| 검수 | 수용 기준 |
|---|---|
| 역할/팀 선택·취소·다시 선택 | 역할명·색/기호·기체·LOS·시작/홈 위치가 일치하고 이전 조종 입력/과제가 남지 않음 |
| 정상 공격 과제와 경계 사례 | 정해진 방향/완전 통과/복귀 조건을 판정, 역방향·부분 통과·리셋을 성공으로 세지 않음 |
| 정상 수비 위치 과제 | 구간 진입·이탈·방향/유지 조건이 정의대로 처리, 접촉 수를 임의 수비 성공으로 변환하지 않음 |
| 비충돌 기준 대상 | 안내 대상이 충돌·득점·경기 자격에 개입하지 않고 화면에서 구분됨 |
| 실제 상대를 도입한 경우 | 사용자 입력 소유권·상대 행동 한계·중단/초기화·통신 장애가 검증된 범위에서만 작동 |
| 과제 완료와 입력 손실/취소 동시 | 사건 순서·보류 정책에 맞고 자동 성공/재ARM/중복 결과 없음 |
| 재시도·조건 변경·재실행 | 이전 시도 보존, 조건 다른 기록 비교 차단, 보정과 비행 안전 상태 보존 |
| 공식 경기로 이동 | Practice 과제·경로/자동 보조·임의 초기화가 공식 경기로 새어 나오지 않음 |
| 한국어·실제 LOS·실물 조종 | 과제 목표와 실패 이유를 읽고 구별 가능. 자동 fixture와 실제 사용성 결과 별도 기록 |

### 15-7. 미정 결정과 진행 조건

구현 전 결정할 사항: 최초 제공 역할/과제 조합, 역할의 한국어 명칭, 목표 구간/방향·시간/속도 허용치, 난이도별 변경 조건, 미선택 기체 처리, 시도 시작/종료·분모, 실제 상대와 비충돌 안내의 우선순위, 관련 규칙 판본과 검토 주체.

결정 전에는 고정 목표 구간의 화면/상태 설계와 테스트 입력/기대 결과 초안을 만들 수 있다. 실기체 전술 효과나 협회 공식 훈련 적합성은 별도 현장/전문 검토 없이 주장하지 않는다. 이 절을 추가한 것은 사용자 요구의 기획 반영이며 아직 포지션별 싱글플레이를 실행할 수 있게 만든 것이 아니다.

### 15-8. 사용자 지정 순서와 역할 설명의 근거

사용자가 지정한 **스트라이커 → 가이드 → 리베로 → 스위퍼 → 골키퍼** 순서로 훈련 메뉴와 설명을 제공한다. 골키퍼는 기존 프로젝트 KEEPER와 연결해 “골키퍼(Keeper)”로 안내하는 안이다. 이 순서는 메뉴/학습 안내 순서이며 경기장 좌우 배치나 모든 과제의 강제 해금 순서가 아니다.

[FIDA Class40 제5차 개정 규정](https://dronesoccer.org/static/files/Rule-book-1.pdf)(2025-10-01 개정·2026-01-01 시행)의 팀 구성 11쪽과 부록 용어집을 확인했다. 해당 판본은 다섯 역할을 구분한다. 스트라이커는 득점, 가이드는 공격 지원과 규정 절차에 따른 스트라이커 대체, 리베로는 전방에서 상대 공격/지원 견제, 스위퍼는 상대 스트라이커의 골 접근 차단, 키퍼는 골 방어로 설명된다. **이 요약은 모든 단체의 규칙이나 팀 전술을 통일하는 설명이 아니다.**

FAI 등 다른 규정 프로필은 별도 판본을 확인해야 한다. 아래 위치·동선·판단·단계·평가 방식은 공식 규정 문장을 옮긴 것이 아니라 **사용자 요청에 따른 훈련 설계 제안**이다. 특히 상대와의 접촉을 횟수 경쟁으로 보상하지 않고 목적·위치·회복·규칙 경계를 함께 검토한다.

### 15-9. 역할별 훈련 요점·단계·평가

각 역할 화면은 **역할 이해 → 기본 조작 → 정해진 상황 → 복합 상황 → 결과/재시도** 틀을 공유한다. 실제 상대가 필요한 과제는 상대 제어·충돌·판정이 검증된 뒤 제공한다.

#### 1. 스트라이커 — 접근·정렬·통과·복귀

- **조작 요점:** 골대 높이로 상승, 접근 속도 줄이기, 방향/옆 이동으로 중심 정렬, 통과 후 자세 회복과 복귀.
- **판단 요점:** 무리한 진입 대신 재접근할 때, 테두리 접촉과 완전 통과의 차이, 현재 과제가 요구하는 복귀 완료 여부.
- **기본 단계:** 정면 고정 시작→접근 구간 정지/정렬→완전 통과→지정 복귀. 다음에는 좌우 다른 시작 각도, 실패 후 재정렬, 표시된 경로 선택으로 확대한다.
- **평가:** 유효 통과/시도, 정렬·접촉·재접근 사건, 복귀 완료를 분리한다. 골대만 통과하고 복귀가 끝나지 않으면 과제 전체 성공으로 표시하지 않는다.
- **복구/확장:** 실패 지점 재시도는 안전 초기화 후 새 시도로 기록. 움직이는 수비·여러 접근 선택·시간 압박은 후속이며 단순 최단 시간이 최적 전술이라는 평가는 하지 않는다.

#### 2. 가이드 — 공격 지원·간격·지원 후 재배치

- **조작 요점:** 동료와 적절한 상대 위치 유지, 지원 구간으로 옆 이동/회전, 접근 동선을 가리지 않는 재배치.
- **판단 요점:** 공격수 경로를 열어 줄 위치, 지원을 계속할지 복귀할지, 동료와 불필요하게 겹치는지.
- **기본 단계:** 고정 동료/수비 표식으로 지원 위치 이해→비충돌 기준 동료 경로를 보며 지원 구간 이동→상황 변경 후 다음 지원/복귀 구간 선택.
- **평가:** 지원 구간 도달·간격·동료 경로 간섭·접촉 사건을 보여준다. 동료 득점만으로 가이드의 공로를 확정하거나 충돌 횟수를 지원 점수로 쓰지 않는다.
- **복구/확장:** 표식 과제에서 잘못된 구간을 골랐다면 이유를 설명하고 같은 장면 재시도. 실제 수비 상대 견제, 공격수 불능 후 승계 절차는 후속이다. 승계는 단순 접촉으로 자동 승인하지 않고 규정·심판 확인 상태 구현 후 별도 과제로 제공한다.

#### 3. 리베로 — 전방 상황 읽기·견제·수비선 복귀

- **조작 요점:** 전방 지정 구간으로 이동, 좌우 접근 방향에 맞춰 위치 전환, 지나친 추격 후 복귀.
- **판단 요점:** 상대 공격/지원 대상 구별, 어느 접근 경로를 우선 관찰할지, 뒤쪽 수비 공간을 비워 두지 않는 지원 선택.
- **기본 단계:** 상대 역할 표식 식별→지정 진입 경로에 대응 구간 이동→두 경로 중 선택→상대가 지나간 뒤 복귀.
- **평가:** 대상 선택·대응 구간 도달·복귀·구간 이탈을 기록한다. 상대 접촉 횟수나 오래 추격한 시간을 좋은 수비로 자동 평가하지 않는다.
- **복구/확장:** 잘못된 대상 선택·늦은 대응·복귀 누락을 별도 안내. 여러 상대/동료와의 분담은 검증된 시나리오와 코치 검토가 필요한 심화 후보다.

#### 4. 스위퍼 — 후방 접근 대응·커버·재정렬

- **조작 요점:** 골대 접근 경로에 맞춘 옆 이동/고도 조절, 지나간 상대 뒤 무리한 추격 대신 기준 구간 재정렬.
- **판단 요점:** 전방을 통과한 공격 경로의 위험, 골키퍼와 겹치지 않는 커버 위치, 대응 뒤 다음 접근을 준비할 때.
- **기본 단계:** 단일 접근 표식→대응 구간 이동/유지→접근 방향 변경→기준 위치 복귀. 이후 전방 방어를 통과한 경로의 선택 과제로 확대한다.
- **평가:** 접근 경로별 대응·구간 점유·골키퍼 경로 간섭·복귀를 나눠 보여준다. 실제 상대 차단 판정 전에는 “차단 성공” 대신 “대응 구간 도달”로 표시한다.
- **복구/확장:** 과도 이동·기준 구간 이탈을 확인하고 같은 방향부터 재시도. 움직이는 공격수·연속 공격·전방/골키퍼 협력은 후속이다.

#### 5. 골키퍼(Keeper) — 골 주변 안정 유지·각도 대응·회복

- **조작 요점:** 골 주변 목표 위치/고도 유지, 좌우·상하 접근에 맞춘 짧은 이동, 골대 접촉 뒤 자세 회복.
- **판단 요점:** 골 주변 위치를 유지할 때와 움직여야 할 때, 접근 각도 변화, 불필요한 이탈/접촉.
- **기본 단계:** 안전한 목표 구간 호버→방향 표시 대응→위치 유지와 복귀→정해진 접근 경로 대응.
- **평가:** 위치/고도 유지·대응 구간·이탈·접촉·복귀를 기록한다. 실제 승인된 득점 기회와 차단 정의가 마련되기 전에는 “선방률”을 계산하지 않는다.
- **복구/확장:** 접촉 후 재정렬 과제는 물리 안정성 확인 뒤 제공. 골대 움직임·득점 영역과 충돌의 일치가 전제다. 실제 상대·연속 공격·수비 제한 규정의 경계 사례는 후속 검수로 분리한다.

### 15-10. 역할 외 공통 조종·실전 상황 훈련

공통 훈련은 모든 역할에서 선택할 수 있게 하되 기존 C04/C09/C10/C12/C15, TRN-01~04/08~10/14/16과 연결한다. 동일 호버/선회 기능을 역할마다 새 기능으로 중복 집계하지 않는다.

| 훈련 묶음 | 조작/판단 과제 제안 | 단계와 평가·복구 |
|---|---|---|
| 기본 비행 | 이륙·호버·직진·옆 이동·선회·착륙 | 기존 첫 비행 단계 재사용. 높이/위치/방향·착륙과 DISARM을 구분 |
| LOS 방향 감각 | 앞/뒤·좌/우 측면 자세에서 입력 방향 이해 | 표식 보조→선택적으로 보조 줄이기. 기체 방향과 화면 방향 혼동 관찰, 보조 사용 기록 |
| 속도/정지점 | 직선 가속 후 감속·목표 구간 진입/정지 | 거리·속도·정지 구간 허용치는 측정 후 결정. 구간 통과와 안정 정지를 구별 |
| 경로 조종 | 8자·S자·지정 게이트 순서 | 고정 경로→다른 진입 각도. 누락/역순/이탈을 설명하고 해당 시작 조건 재시도 |
| 접근·회피 | 장애물/동료 표식과 간격 유지, 막힌 경로에서 돌아가기 | 비충돌 표식부터. 실제 접촉 물리 상대는 후속, 순간이동 회피 금지 |
| 충돌 후 회복 | 벽·네트·골대 접촉 뒤 방향/고도 회복 | 검증된 낮은 난도의 접촉 조건부터. 회복·추가 접촉·안전 중단 구분, 실제 파손 재현 보장 아님 |
| 복귀와 재출발 | 과제 신호 뒤 지정 복귀·다음 출발 준비 | 단계 사건·복귀 누락 표시. 공식 오프사이드/재공격 자격 판정과 구별 |
| 제한 상황 | 시간/점수 차·동료 일부 불능·역할 전환의 판단 | 상태 설명/정해진 시나리오부터. 실제 규정·논리 고장/승계 구현 전에는 절차 학습 후보 |
| 연속 시도 | 같은 조건의 반복과 체력/집중 저하 관찰 | 시도별 결과·중단·보조 조건 보존. 피로/실력의 원인을 로그만으로 단정하지 않음 |
| 입력·출력 이상 대응 | USB 손실·포커스 손실·출력 제한 경고 이해 | 위험 시험은 별도 안내/동의된 시험에서 수행. 초보 정상 훈련 중 예고 없이 연결 장애를 강제하지 않음 |

실전 상황 과제는 관찰한 경기 영상/코치 검토와 규정 근거가 확보된 범위부터 설명한다. 임의로 만든 시나리오는 “연습 시나리오”로 표시하며 실제 대회 전술 통계에서 도출됐다고 주장하지 않는다.

### 15-11. 제공 순서·검수와 아직 정하지 않은 것

**메뉴 순서**는 사용자 지정 다섯 역할을 유지한다. **구현 순서**는 공통 조종/과제 엔진→스트라이커의 고정 접근/통과와 수비의 고정 위치 과제→가이드/리베로/스위퍼/골키퍼 각각의 표식·경로 판단 과제→검증된 움직이는 상대/복합 상황 순으로 제안한다. 메뉴 순서와 개발 순서를 구별하고 미구현 역할 과제에는 준비 중을 표시한다.

모든 역할의 첫 목표·성공/실패·다시하기 안내는 한국어로 제공하고 같은 입력/저장/ARM 계약을 재사용한다. 역할 변경 시 기체·LOS·표시·과제/결과 조건은 갱신하지만 개인 보정은 보존한다.

- 역할별 검수는 기본 성공뿐 아니라 잘못된 대상/방향·구간 이탈·복귀 누락·접촉·중단·재시도를 포함한다.
- 역할별 판정이 선수 기량 평가로 과장되지 않는지 검토한다. 가이드 지원·수비 차단·선방의 인과 평가에는 정답 사건/코치 검토가 필요하다.
- 비충돌 표식→물리 상대 전환 시 동일 과제 이름이어도 조건/평가 버전을 바꿔 기록하고 기존 성적과 무조건 합치지 않는다.
- 선택한 역할이 득점 자격·승계·심판 권한을 자동 변경하지 않는지 검사한다. 공통 과제와 공식 경기 간 상태 유출도 확인한다.
- 실물 조종·양 팀 LOS·화면 배율·한국어 오류/복구를 별도로 검수하고 자동 과제 판정만으로 전체 역할 훈련 완료를 주장하지 않는다.

미정: 각 역할의 첫 제공 과제 수, 목표 위치·간격/시간/속도 허용치, 표식/상대 난이도, 규정 판본별 경계, 사용자가 원하는 팀 전술 차이, 코치 검토 범위와 참여 가능 여부. 정하지 않은 수치를 임의 확정하거나 전문가 연락/참여가 이미 이뤄졌다고 표시하지 않는다.

## 16. 훈련 지표·판정·피드백의 일관성 계약

11절은 결과 화면과 저장 상태, 15절은 역할별 과제를 정의한다. 이 절은 **같은 사건을 어떤 시도로 세고 어떤 말로 설명할지**를 맞춘다. C08/C15, TRN-12, DAT-13~15, QA-12/13과 연결하며 구현된 통계 시스템이나 확정된 교육 효과를 뜻하지 않는다.

### 16-1. 세션·시도·단계·사건을 구분한다

- **세션:** 한 번의 연습 진행 묶음. 여러 시도가 들어갈 수 있다.
- **시도:** 시작 조건 확인 뒤 명시적으로 시작한 한 과제. 재시도는 새 식별자를 받으며 이전 기록을 덮지 않는다.
- **단계:** 접근→통과→복귀처럼 시도 안의 세부 목표. 단계 성공과 시도 전체 성공을 구분한다.
- **사건:** 구간 진입·통과·접촉·연결 손실·취소 등 판정 근거. 같은 접촉이나 종료 알림이 반복됐다고 시도를 늘리지 않는다.

시도 시작 전 취소/로딩 실패는 과제 시도로 집계하지 않되 준비 실패 기록으로 남긴다. 시작 후 취소/입력 손실은 시도 존재를 보존하고 중단 사유를 기록한다. 이 경계는 모든 역할과 공통 훈련에서 동일하게 적용한다.

### 16-2. 판정 상태와 분모

| 상태 | 적용 기준 | 집계 원칙 |
|---|---|---|
| 성공 확정 | 필요한 모든 단계의 성공 조건과 유효 증거 충족 | 성공 시도에 포함. 단계 하나만 완료한 경우 제외 |
| 실패 확정 | 사전에 정한 과제 실패 조건이 증거로 확인됨 | 실패 시도에 포함. 접촉 자체가 실패인지 여부는 과제 정의를 따름 |
| 사용자 중단 | 진행 중 사용자가 종료/재시도 선택 | 중단으로 별도 표시. 성공/실패로 임의 변환하지 않음 |
| 안전/환경 중단 | USB 손실·앱/환경 문제 등으로 과제를 끝내지 못함 | 원인과 완료 구간 표시. 사용자 실수나 실력 점수로 바꾸지 않음 |
| 판정 보류 | 동시 사건 순서·증거 누락·조건 불일치로 판정 불가 | 계산 불가/보류 표시. 0점 또는 성공으로 대체하지 않음 |

**표시 초안:** 성공률을 제공한다면 “판정 완료 시도 중 성공 = 성공 확정 / (성공 확정 + 실패 확정)”이라고 분모를 명시하고, 전체 시작 시도·사용자 중단·안전/환경 중단·보류를 함께 보여준다. 분모가 0이면 “아직 계산할 수 없어요”로 표시한다. 중단이 많을 때 높은 판정 완료 성공률만 단독 강조하지 않는다.

중단을 숨기고 성공한 시도만 선택할 수 있는 순위표는 초기 범위에 포함하지 않는다. 나중에 경쟁 기록을 제공한다면 중단/재시도·검증 정책부터 별도로 정한다.

### 16-3. 첫 제공 지표 정의

| 지표 | 정의 초안 | 필요한 제약 |
|---|---|---|
| 유효 통과 횟수 | 방향·완전 통과·과제 자격을 충족한 고유 통과 사건 수 | 부분 진입/반등/동일 사건 중복 제외. 경기 승인 득점과 별도 |
| 최고 연속 성공 | 같은 과제·평가 버전·조건의 연속된 성공 확정 시도 길이 | 실패는 연속 종료. 중단/보류·조건 변경을 건너뛰어 연속을 연결하지 않음 |
| 구간 유지 | 유효 관측 구간 중 목표 조건을 만족한 지속 시간/비율 | 시간 기준·누락·중단을 명시. 관측 안 된 구간을 유지 성공으로 채우지 않음 |
| 완료 시간 | 사전 정의한 시작 사건부터 과제 전체 완료 사건까지의 해당 시계 시간 | 시간 예산/정지 정책 표시. 실패/중단을 짧은 완료 시간으로 순위화하지 않음 |
| 복귀 시간 | 복귀 시작 사건부터 복귀 조건 완료까지 | 미복귀는 미완료. 첫 접촉/구간 스침을 안정 복귀로 바꾸지 않음 |
| 접촉 사건 | 정한 기체 쌍/대상·접촉 구간으로 묶은 고유 사건 | 프레임마다 증가시키지 않음. 수비/지원의 좋은 성과로 자동 환산하지 않음 |
| 위치·방향 오차 | 과제가 정의한 좌표계/목표에 대한 유효 표본의 오차 | 단위·구간·요약 방식·누락을 명시. 목표 자체가 움직이면 그 시각의 목표와 비교 |

각 지표는 정의/평가 버전을 갖고 계산 입력과 제외 이유를 추적할 수 있어야 한다. 정확도/속도 목표가 다르면 같은 이름의 지표도 비교 조건을 확인한다. 복합 가중 점수·“수비력”·“팀 기여도”는 별도 근거가 없어 초기에는 제공하지 않는다.

### 16-4. 관찰에서 한국어 피드백으로 연결

| 관찰된 근거 | 허용할 피드백 예시 | 피할 표현 |
|---|---|---|
| 통과 완료·복귀 미완료 | “골대는 통과했어요. 복귀 단계는 끝나지 않았어요.” | “득점 성공, 훈련 완료”로 전체를 합침 |
| 대응 구간에 늦게 도달 | “상대 표식이 지난 뒤 목표 구간에 도착했어요.” | 실제 물리 상대/득점 기회가 없는데 “선방 실패” |
| 구간 이탈 확인 | “목표 구간을 벗어났어요. 위치를 다시 맞춰 봐요.” | “집중력이 부족해요”처럼 원인을 추정 |
| 입력 손실로 중단 | “조종기 입력이 끊겨 연습을 중단했어요.” | 사용자 조종 실패로 점수 차감 |
| 표본 부족·판정 보류 | “기록이 부족해 이번 결과를 확정하지 못했어요.” | 근거 없는 성공/실패 또는 0초/0점 |

권장 행동은 확인된 과제 기준과 연결한다. “다음에는 접근 구간에서 정렬해 봐요” 같은 제안은 관찰 사실과 분리해 표시하고 유일한 정답 전술처럼 단정하지 않는다. 같은 오류를 반복할 때 설명/기초 과제 선택을 제공하되 몰래 난이도를 바꾸지 않는다.

### 16-5. 데이터 변경·보존과 검수

원시 사건, 최초 판정, 정정 판정, 표시 지표를 논리적으로 구분한다. 평가 정의가 바뀌어 과거 기록을 재계산하는 경우 원래 값·새 평가 버전·변경 이유를 남기고 과거 기록을 조용히 덮어쓰지 않는다. 개인 저장의 보관 기간·용량·삭제 UI는 미정이며 무기한 수집을 기본 약속하지 않는다. 사용자 삭제 요청의 범위와 실현 여부는 별도 기능으로 확인한다.

| 검수 입력 | 기대 결과 |
|---|---|
| 같은 완료/통과 이벤트 중복 수신 | 시도·성공·통과가 중복 집계되지 않음 |
| 통과 성공 뒤 복귀 전에 취소 | 단계 성공 보존, 시도는 중단, 전체 성공률 분자에 넣지 않음 |
| 성공→중단/보류→성공 | 두 성공을 끊김 없는 연속 성공으로 합치지 않음 |
| 목표/보조/평가 버전 변경 | 조건 다른 기록 비교/연속 집계 분리 |
| 누락 구간에 목표 이탈 가능 | 유지 성공을 보간으로 확정하지 않고 증거 한계 표시 |
| 저장 실패 후 같은 결과 재저장 | 결과 식별자 유지, 재시도로 중복 성적 생성하지 않음 |
| 판정 정정·평가 버전 갱신 | 최초 근거/판정과 새 결과를 구분, 수정 사유 표시 |
| 확정 성공/실패가 없는 세션 | 성공률 계산 불가, 중단/보류 수는 확인 가능 |

구현 전에 확정할 것: 과제별 실패 사건, 접촉 구간 묶음 기준, 시각/좌표계, 관측 누락 판정, 기록 보관/삭제 범위, 정정 권한과 사용자 표시. 현재는 제품 데이터 계약 제안이며 실제 로그 형식·판정 구현·보존 기능을 새로 완료한 것이 아니다.

## 17. 역할 훈련 시나리오의 구현 인계 계약

15절의 과제와 16절의 지표를 개발에 넘길 때 필요한 **시나리오 정의·판정 사건·검수 자료**를 묶는다. TRN-05~09/14/16, DAT-14/15, QA-12/13에 연결하며 새 기능 번호나 구현 API를 확정하지 않는다.

### 17-1. 과제 하나를 정의하는 최소 자료

| 정의 항목 | 필요한 내용 | 준비되지 않았을 때 |
|---|---|---|
| 식별/호환 | 시나리오·평가 버전, 연결 역할/기능, 지원 규칙/모드 | 이전 이름이 같아도 다른 판정을 임의 혼합하지 않음 |
| 공간/시간 | 좌표계·단위·기준 팀/진영, 사용하는 시계, 구간 경계의 포함/제외 | 기하 판정/시간 기록 구현 착수 전 결정 |
| 시작 상태 | 사용자 기체·LOS·기체/배터리·보조·장치 준비, 미선택 기체 상태 | 안전 준비를 통과하지 못하면 시작 거부, 기존 보정 보존 |
| 장면 요소 | 목표/복귀 구간, 비충돌 표식 또는 물리 상대, 각 요소 식별자 | 없는 상대/목표를 원점의 기본 객체로 대신 만들지 않음 |
| 단계/전이 | 단계별 진입·완료·실패·중단 조건과 필요한 사건 | 항상 참인 기본값으로 자동 완료하지 않음 |
| 평가/피드백 | 지표 정의·분모·한국어 근거/다음 행동, 정정/보류 정책 | 근거 없는 점수 대신 미지원/판정 보류 |
| 복구/기록 | 취소·재시도·reset 범위, 저장 조건 지문과 증거 필드 | 새 시도와 이전 결과가 섞이지 않는 경계부터 설계 |
| 검수 자료 | 정상/경계/실패 사건열, 기대 단계·결과·금지 동작 | 예시 화면만으로 판정 완료 처리하지 않음 |

정의 로딩 시 유한 수치·단위·필수 대상·단계 참조·도달 가능한 종료·비정상 순환을 검사하는 방안을 설계한다. 구간 크기/시간이 없거나 잘못된 값이면 사용자에게 준비되지 않은 과제임을 알리고 시작을 거부한다. 외부 시나리오 가져오기/공유는 별도 후속이며 임의 코드나 명령을 실행하는 형식으로 설계하지 않는다.

### 17-2. 공통 판정 사건과 권한

논리 사건 예시는 **시도 시작, 구간 진입/이탈, 유효 통과, 접촉, 목표 변경, 입력 손실, 사용자 중단, 초기화, 단계 완료, 시도 종료**다. 명칭은 설계 예시이며 현재 코드에 같은 이벤트 버스가 있다고 주장하지 않는다.

- 사건에는 시도/기체/대상·세대·고유 식별자, 발생 시각/시계·물리 step, 출처, 유효성/누락 정보를 연결한다. 게임에서 받은 순서와 물리적으로 발생한 순서를 혼동하지 않는다.
- 사용자 입력·물리 관찰은 근거이고, 과제 판정기는 그 근거를 현재 단계/정의에 적용한다. 결과 UI가 버튼 클릭이나 애니메이션 종료만으로 성공 사건을 만들어 내지 않는다.
- 비충돌 표식의 구간 통과는 훈련 사건이다. 물리 상대 접촉·공식 득점/승계와 같은 권한으로 다루지 않는다.
- 안전 처리는 과제 판정 대기와 독립적으로 적용한다. 동시 성공/입력 손실의 점수 해석이 미정이어도 DISARM 등 기존 안전 동작을 기다리게 하지 않는다.
- 종료된 시도나 reset 이전 세대의 늦은 사건은 새 시도를 변경하지 못한다. 중복 사건은 식별자로 구분하고 반복 알림을 추가 성공으로 집계하지 않는다.
- 사건 누락/순서 불명은 16절의 보류 정책으로 연결한다. 사용자가 유리해지는 순서로 사건을 임의 재배열하지 않는다.

### 17-3. 첫 구현 묶음의 의존성

| 작은 구현 묶음 | 재사용할 기반·선행 | 새로 검수할 핵심 |
|---|---|---|
| 공통 과제 정의/상태 | 기존 입력/안전·진영/LOS·시간 계약 | 정의 검증, 시도/세대 분리, 단계/종료의 단일 판정 |
| 정적 위치 유지 과제 | 목표 구간/시계·유효 표본 | 진입→유지→이탈/완료, 누락·경계 진동 처리. 수비 위치·호버에 재사용 |
| 공격 접근→통과→복귀 | 골대 통과 근거·단계별 목표 | 통과만으로 전체 성공 금지, 복귀까지 완료, 역방향/리셋 배제 |
| 지원/대응 표식 과제 | 비충돌 표식·목표 변경 사건 | 가이드/리베로/스위퍼/골키퍼 과제 조건 분리, 표식이 물리/득점에 개입하지 않음 |
| 결과·재시도 연결 | 11절 저장 상태·16절 지표 | 사건→판정→표시→저장 동일성, 이전 시도 보존 |
| 물리 상대/복합 전술 | 상대 소유권·힘 기반 행동·충돌/통신 검증 | 신규 조건으로 재검수. 표식 과제 통과를 전술 상대 검증으로 재사용하지 않음 |

새 상대 AI가 없어도 정적 구간/비충돌 표식의 초기 과제를 검토할 수 있다. 반대로 메뉴만 구현한 상태를 과제 판정 완료로 표시하지 않는다. 공통 기능을 재사용하되 역할별 조건·메시지의 정확성은 각각 검사한다.

### 17-4. 개발자가 받을 사건열 기반 검수 예시

| 사건열 예시 | 기대 판정·금지 동작 |
|---|---|
| 준비→명시적 시작→목표 진입→유지 조건 충족 | 위치 유지 과제 완료. 구간 스침만으로 유지 조건 생략 금지 |
| 목표 진입→이탈→재진입 | 이탈/재진입 기록. 누적 유지인지 연속 유지인지 사전 정의를 따르고 임의 혼합 금지 |
| 접근→유효 골대 통과→복귀 전 중단 | 통과 단계만 완료, 시도는 중단. 전체 성공 생성 금지 |
| 접근→부분 통과/역방향→reset | 실패/진행 여부는 과제 정의, reset은 새 세대. 순간 배치로 통과 사건 생성 금지 |
| 목표 A→목표 B로 변경→늦은 A 완료 | B 과제 상태 보존. 이전 목표의 사건으로 완료 금지 |
| 성공 후보→입력 손실, 순서 불명 | 안전 동작 우선, 판정은 정의에 따라 보류. 자동 재개·근거 없는 성공 금지 |
| 시도 종료→같은 사건 재수신→재시도 | 종료 결과 한 번, 새 시도 식별자 분리, 이전 사건 적용 금지 |
| 올바르지 않은 정의/없는 대상→시작 요청 | 이유 있는 시작 거부, 정상 프로필·메뉴 복구 유지 |

이 사건열 시험은 판정 로직 검수다. 실제 엔진이 올바른 시각/대상으로 사건을 만드는지 확인하는 공간 경계·충돌·화면·실물 시험은 별도다. 두 계층을 각각 통과해야 해당 과제의 검증 범위를 설명할 수 있다.

**인계 출구:** 시나리오 정의, 미정 조건, 판정 책임, 사건열과 기대 결과, 실제 장면 검수 목록, 연결 기능/후보가 서로 대응해야 한다. 아직 없는 좌표·허용치·상대 행동·실행 결과는 미정/미실행으로 남기며 형식 초안을 실행 가능한 콘텐츠로 소개하지 않는다.

### 17-5. MVP 과제 채택 카드와 보류 기준

15절의 넓은 후보를 한 번에 구현하는 대신, 첫 개발 인계에서는 아래 **두 과제 유형의 채택 여부**부터 검토한다. 이는 구현 우선순위 제안이며 두 과제의 출시나 모든 역할 지원을 확정하는 결정이 아니다. 메뉴는 사용자 지정 다섯 역할 순서를 유지하되, 같은 공통 호버 과제에 이름만 바꿔 붙여 다섯 역할 훈련 완료로 집계하지 않는다.

| 우선 검토 과제 | 채택 전에 확보할 최소 근거 | 없을 때의 보류·축소 |
|---|---|---|
| 수비 기초: 지정 위치 유지 | 실제 장면의 목표 구간·방향 기준, 연속/누적 유지 중 선택, 이탈 시 처리, 표본 누락 정책, 정상·경계·이탈 사건과 화면의 대응 | 역할별 목표를 설명할 근거가 없으면 ‘공통 위치 유지’ 시제품으로만 검토. 실전 수비·선방 평가를 붙이지 않음 |
| 공격 기초: 접근→통과→복귀 | 실제 골대와 판정 영역의 일치, 진입 방향/완전 통과 근거, 복귀 구간, 부분 통과·reset 배제, 세 단계 결과 분리 | 통과 근거가 미검증이면 접근/정렬 시제품까지만 검토. 골대 통과 성공이나 전체 과제 완료를 대체 애니메이션으로 만들지 않음 |

각 과제의 채택 카드에는 17-1절 자료를 반복 복사하지 않고 해당 정의·시험 증거를 연결한다. **미정 조건 / 결정한 값과 이유 / 결정 검토자 / 적용 버전 / 미실행 시험**을 짧게 남기고, 검토자를 실제 배정하지 않았다면 미정으로 표시한다. 목표 위치·시간·허용 오차는 화면상 편의로 임의 확정하지 않는다.

개발 인계 가능과 사용자 제공 가능은 다음처럼 구분한다.

- **정의 검토 가능:** 목표·사용자 행동·미정 조건이 식별됨. 아직 구현 착수나 정상 판정 보장 아님.
- **판정 구현 착수 가능:** 좌표/시간·단계·경계·종료 조건과 기대 사건열이 확정됨. fixture 통과만으로 실제 장면 검수 완료 아님.
- **내부 시제품 확인 가능:** 실제 장면에서 사건 출처·화면/결과 일치·중단/재시도를 확인할 수 있음. 실물 조종·초보 사용성 미실행 범위를 표시.
- **제공 후보:** 선택한 입력 방식과 지원 환경의 안전/사용성 검수 증거가 연결되고, 미지원 역할·평가 한계가 화면에 드러남. Boxer 미감지 해결 전에는 해당 장치 검증 완료로 표시하지 않음.

한 과제의 보류가 다른 과제의 안전 게이트를 완화하지 않는다. 검수 가능한 과제만 별도로 진행하되 미검증 과제를 자동으로 ‘준비 완료’로 바꾸지 않는다. 실제 개발 일정·출시 범위는 이 채택 검토와 구현 결과 이후 결정한다.

### 17-6. 결과 화면·코치 연결용 합성 정답 예시

기존 16절의 분모와 단계 구분을 개발자가 그대로 대조할 수 있도록 작은 정답표를 둔다. **아래는 사람이 작성한 합성 입력/기대값이며 실제 비행 기록·실행한 테스트가 아니다.** 좌표·시간 임계값을 확정하지 않고 판정기가 이미 확정한 사건을 집계하는 계층만 검사한다. 모든 시도는 같은 과제/평가 버전·조건이다.

| 시도 | 합성 사건 | 기대 최종 상태 |
|---|---|---|
| A | 시작→통과 E1→같은 E1 중복 수신→복귀 완료 | 성공 확정 1회, 유효 통과 1회 |
| B | 시작→과제 정의상 실패 확정 | 실패 확정 1회 |
| C | 시작→통과 E2→복귀 전 사용자 종료 | 사용자 중단 1회, 통과 단계만 완료 |
| D | 시작→입력 손실로 종료 | 안전/환경 중단 1회 |
| E | 시작→종료 후보 사건의 순서/근거 부족 | 판정 보류 1회, 임의 성공/실패 금지 |

**정답:** 전체 시작 5, 성공 1, 실패 1, 사용자 중단 1, 안전/환경 중단 1, 보류 1. 판정 완료 시도 중 성공률은 1/(1+1)=50%이며 중단/보류 수를 함께 보여준다. 유효 통과 횟수는 2, [코치 계획 4.1절](ai-coach-detailed-plan-2026-10-28.md)의 전체 시작 기준 통과 시도 비율은 2/5=40%다. 최고 연속 전체 성공은 1이며 C의 통과를 전체 성공으로 더하지 않는다. 중복 E1을 다시 넣어도 값은 변하지 않아야 한다.

**인수 연결:** 결과 화면·저장 후 다시 읽은 결과·오프라인 설명·AI 응답 검증기의 기준값을 위 정답표와 대조한다. AI 경로는 먼저 mock 응답으로 검사하며 유료 호출이 필요하지 않다. E를 새 근거로 정정하는 별도 사례에서는 원래 보류 기록과 새 판정 버전을 보존하고 이전 설명을 현재 결과로 표시하지 않는다. 구체적인 정정 결과는 추가 사건으로 명시해야 하며 표의 빈 증거를 추정해 채우지 않는다.

## 18. 배포 검사 결과의 최종성·파일 집합·출처 검수

8절의 산출물 관문을 **거짓 성공을 막는 판정 규칙**으로 구체화한다. QA-11/12, REL-02/03/05/10과 연결한다. [현재 배포 검사 코드](../Tests/test-portable-release.py)를 정적으로 대조했으며 이번에 검사 실행·결함 재현·코드 수정·새 배포를 수행하지 않았다.

### 18-1. 정적 검토에서 구분한 위험

현재 코드는 새 출력 폴더를 만들고 확인 항목마다 결과 JSON을 기록한다. 체크섬 목록에 적힌 파일의 해시와 경로 범위, 피드백 HTML의 필수 포함/원본 일치, 개인 설정 제외, 실행기·APF·저장 검사 경로도 있다. 이 기반을 삭제하거나 “검사가 전혀 없다”고 설명하지 않는다.

다만 중간 확인 항목까지 모두 참이면 그 시점의 결과에 성공 값이 기록될 수 있고, 이후 예외가 최종 실패 보고서를 남기지 못하면 중간 성공 파일만 남을 가능성이 있다. 또한 목록의 모든 행을 검사하는 것과 **필요한 모든 파일이 목록에 들어 있는지** 확인하는 것은 다르다. 이는 정적 위험이며 과거 통과 기록 전체가 잘못됐다고 판정하는 근거가 아니다.

### 18-2. 최종 보고서 계약

- 실행 시작 시 실행 ID·대상 빌드/ZIP 지문·검사 계획 버전·필수/선택 검사를 고정한다. 진행 중 결과는 최종 성공으로 읽히지 않는 상태를 갖게 설계한다.
- 최종 성공은 모든 필수 단계의 종료, 각 결과의 유효성, 대상 출처 일치, 검사 프로세스의 정상 종료를 함께 확인한 경우에만 허용한다. 검사 목록이 비었거나 중간 단계까지만 수행된 것은 성공이 아니다.
- 예외·시간 초과·비정상 자식 종료·결과 파일 누락은 실패/중단 사유와 마지막 단계로 보고한다. 선택 검사의 미실행은 범위에 남기고 전체 현장 검증으로 확대하지 않는다.
- 프로세스 강제 종료 등으로 최종 파일 자체를 못 쓰면 소비자가 미완료로 판단해야 한다. “파일이 있으니 성공”이나 “기존 ok 값이 참이니 성공”으로 해석하지 않는다.
- 보고서와 종료 코드를 함께 소비하는 상위 집계도 검수한다. 보고서 쓰기 실패는 콘솔/프로세스 상태 등 대체 근거로 드러내고 성공으로 숨기지 않는다.
- 새 실행의 결과 경로는 이전 실행과 분리한다. 최종 기록의 중간 쓰기/부분 JSON을 정상 완료로 읽지 않도록 저장 방식과 읽기 검사를 설계한다.

### 18-3. 체크섬 검사는 세 집합을 대조한다

| 집합 | 정의·용도 |
|---|---|
| 기대 배포 파일 | 빌드/패키징 규칙이 요구하는 필수 파일과 허용하는 선택 파일. 누락돼도 체크섬 작성기가 함께 빼 버릴 수 없도록 검사 기준을 분리 |
| 체크섬 목록 | 검증 대상 상대 경로·해시. 중복·잘못된 형식·빈 목록·허용되지 않은 경로를 검사 |
| 실제 압축 해제 파일 | 새 경로에 해제한 실제 파일. 필수 누락·뜻하지 않은 추가·개인 설정/생성 데이터 포함을 확인 |

목록과 실제 파일의 일치뿐 아니라 기대 집합과의 대응을 확인한다. 체크섬 파일 자신·서명/외부 메타데이터 등 예외가 필요하면 경로·이유·다른 검증 방법을 명시한다. 변조 파일만 검사하는 것으로 필수 파일 누락 검수를 대신하지 않는다.

경로의 대소문자/구분자·정규화 뒤 중복, 절대 경로·상위 이동·해제 위치 밖을 가리키는 링크/경로도 플랫폼 특성에 맞춰 검토한다. 실패 경로를 자동 수정하거나 외부 파일을 읽어 통과시키지 않는다. 기존 실행본이나 개인 보정을 파괴하는 방식으로 장애를 주입하지 않고 별도 시험 복사본을 사용한다.

### 18-4. 해시 무결성과 빌드 출처는 별도다

실제 소스/콘텐츠/설정 입력 지문→빌드 manifest→실행본의 버전/입력 지문→배포 manifest/파일 집합→ZIP 해시→검사 결과의 대상 식별을 연결한다. ZIP과 체크섬이 서로 맞는 것만으로 그 실행본이 의도한 소스로 빌드됐다고 증명하지 않는다.

소스가 변경됐는데 오래된 바이너리/manifest가 섞인 경우, 실제 검사한 실행본과 배포 ZIP이 다른 경우, 결과 파일이 다른 빌드를 가리키는 경우를 별도 실패 사례로 둔다. 문서만 바뀐 커밋과 실행 입력이 바뀐 커밋의 차이는 빌드 입력 범위로 설명하고 무조건 동일한 Git HEAD 문자열만 요구하지 않는다. 입력 범위에 포함/제외한 경로와 근거가 필요하다.

### 18-5. 장애 주입 검수와 공개 판단

| 시험 복사본에 주입할 조건 | 기대 결과 |
|---|---|
| 첫 확인 성공 뒤 다음 단계 예외 | 중간 성공 파일이 남아도 최종 집계는 성공 아님, 마지막 단계/사유 식별 |
| JSON 파싱 실패·부분 기록·오래된 결과 | 해당 실행의 유효 최종 결과로 인정하지 않음 |
| 자식 시간 초과/비정상 종료, 보고서 쓰기 실패 | 실패/중단 근거를 남기거나 미완료로 감지, 성공 잔존 금지 |
| 필수 파일을 실제 파일과 목록 양쪽에서 삭제 | 기대 집합과 대조해 누락 거부 |
| 해시 변조·중복/별칭 경로·목록 밖 추가 파일 | 해당 불일치/정책 위반을 명시, 허용 예외는 사전 정의만 인정 |
| 이전 실행본/다른 manifest/다른 빌드 결과 혼합 | 출처 연결 불일치로 거부 |
| 개인 보정/생성 사용자 데이터 포함 | 기존 제외 정책 유지, 공개 산출물로 채택하지 않음 |
| 선택 실물/다른 PC 검사 미실행 | 소프트웨어 검사 범위만 표시, 현장 검증 완료로 집계하지 않음 |

검사기 자체의 실패 처리 검수와 실제 제품 기능 검수는 서로 다른 결과다. 배포 채택은 두 결과의 필요한 범위를 모두 확인한 뒤 판단하며, 이 계획 등록은 기존 릴리스 교체·삭제·재업로드를 승인하거나 실행한 것이 아니다.

## 19. 역할·과제 선택 화면의 포커스와 맥락 복구

기존 화면 지도에 없는 **선택 상태와 조작 포커스의 관계, 오류 뒤 어디로 돌아오는지**를 구체화한다. SYS-03/04, UX-03/06/07/10/12, INP-10, TRN-08과 연결한다. 키보드 접근성·화면 읽기 보조 지원을 현재 구현 완료로 주장하지 않는다.

### 19-1. 화면별 정보 순서와 선택 상태

| 화면 | 먼저 읽을 내용 | 기본 조작 위치·복귀 맥락 제안 |
|---|---|---|
| 포지션 선택 | 제목→선택된 역할→역할 목적→사용 가능 과제→다음/뒤로 | 스트라이커·가이드·리베로·스위퍼·골키퍼의 사용자 지정 순서. 최초 기본 역할 선택 여부는 명시하고 포커스만 이동했다고 자동 확정하지 않음 |
| 훈련 과제 선택 | 현재 역할→과제 이름/목표→기초/심화·보조 조건→준비 상태 | 이전 선택 과제가 있으면 강조하되 실행 가능성 재확인. 없는/변경된 과제를 조용히 다른 것으로 대체하지 않음 |
| 시작 조건 확인 | 역할/과제→현재 장치/모드→기체·보조·평가 조건→시작을 막는 항목 | 수정이 필요한 항목으로 이동할 수 있게 함. 설정 복귀 뒤 같은 과제/조건 요약을 다시 확인 |
| 중단 확인 | 중단할 시도→기체 안전/저장 영향→계속/중단 | 실수로 중단을 확정하지 않는 기본 선택 제안. 공중 상태와 실제 조작 허용은 11절 안전 계약 우선 |
| 결과 | 완료/중단/보류→요약→저장 상태→다시하기/다른 과제/메인 | 결과가 나타난 순간 입력이 재시도로 이어지지 않게 함. 선택만으로 새 시도 생성 금지 |
| 오류 복구 | 실패한 동작→유지된 선택/설정→가능한 복구→뒤로 | 오류를 닫으면 호출한 항목 또는 유효한 인접 항목으로 복귀. 성공 화면으로 잘못 이동하지 않음 |

“선택됨”, “현재 키보드 포커스”, “마우스가 올라감”, “사용 불가”를 서로 다른 시각/문자로 표현한다. 역할색만으로 선택 여부를 표시하지 않는다. 준비 중 항목도 이유와 돌아가는 방법을 확인할 수 있어야 하며 동작하지 않는 빈 버튼처럼 만들지 않는다.

### 19-2. 탐색·확인·뒤로가기 계약

- 키보드만으로 항목 탐색·설명 확인·선택·뒤로가기가 가능하도록 순서와 키 안내를 설계한다. 실제 키 배정은 기존 게임/보정 단축키와 충돌 검토 후 확정한다.
- 탐색은 포커스를 옮기는 동작이고 확인은 선택을 적용하는 동작이다. 비행 축 입력을 메뉴 탐색에 자동 연결하는 것은 이번 범위가 아니며 지원할 경우 드리프트/연속 입력·ARM 스위치 충돌부터 검증한다.
- 설명 창/확인 창이 열리면 입력은 해당 창의 허용 동작으로 제한한다. 뒤의 시작/ARM/재시도 버튼이 동시에 실행되지 않게 한다.
- 창을 닫을 때 호출 항목으로 포커스를 돌리고, 항목이 사라졌다면 화면 제목/유효한 선택 위치로 복귀한다. 보이지 않는 요소에 포커스가 남지 않게 한다.
- 검색/필터 같은 기능은 아직 범위로 추가하지 않는다. 과제 목록이 길어질 때 스크롤 중 선택/포커스 유지와 현재 위치 표시부터 검토한다.
- 연결 상태/저장 결과 갱신은 사용자가 읽는 설명을 갑자기 닫거나 포커스를 이동시키지 않는다. 안전상 필수 알림은 접근 가능하게 표시하되 종료/ARM 같은 행동을 대신 확정하지 않는다.

### 19-3. 오류 뒤 보존할 것과 다시 확인할 것

| 상황 | 보존할 맥락 | 재확인이 필요한 상태 |
|---|---|---|
| 조종기 설정으로 이동했다 복귀 | 역할·과제·선택한 보조/평가 목표, 돌아올 항목 | 실제 장치·보정·입력 유효성·스로틀/ARM 상태 |
| 로딩 취소·실패 | 선택한 과제와 조건 요약·실패 이유 | 부분 생성 객체/이전 요청 정리와 새 시작 가능 여부 |
| 과제 정의 갱신/삭제 | 이전 선택의 식별자와 변경 안내 | 새 정의의 조건/평가 버전, 기록 비교 가능성 |
| 결과 저장 실패 | 현재 시도 결과와 사용자의 다음 행동 선택 | 실제 저장 여부·재시도 중복 여부 |
| 화면 배율·크기 변경 | 선택·현재 화면/설명 맥락 | 버튼 가시성·문구 잘림·스크롤/포커스 위치 |
| 앱 전환 후 복귀 | 메뉴의 비파괴적 선택 맥락 | 입력 안전 상태. 메뉴 위치 복원을 비행 자동 재개로 연결하지 않음 |

영구 저장할 선택과 한 세션에서만 보존할 선택은 구현 시 구분한다. 장치 연결/ARM·물리 실행 상태는 이전 화면 선택을 복원했다는 이유로 복원하지 않는다.

### 19-4. 접근성·맥락 회복 수용 검사

- 마우스 없이 다섯 역할을 순서대로 확인하고 과제를 선택·취소·다시 선택해 시작 조건 화면으로 이동할 수 있는지 확인한다.
- 역할색을 구별하기 어려운 조건에서도 텍스트/기호와 선택 표시로 역할·포커스·사용 가능 상태를 구분하는지 확인한다.
- 준비 중 과제, 긴 한국어 제목, 빈/삭제된 과제, 여러 줄 오류에서 설명과 뒤로가기를 읽고 실행할 수 있어야 한다.
- 설명 창을 열고 Enter/Space/뒤로가기 키를 누르거나 길게 유지해도 배경의 시작·ARM·중단 확정이 실행되지 않아야 한다.
- 장치 상태가 바뀌거나 저장 응답이 늦게 와도 선택한 과제/현재 창이 다른 것으로 바뀌지 않아야 한다.
- 화면 크기/배율 변경과 스크롤 후에도 포커스 항목을 볼 수 있고, 마우스 이동만으로 선택 조건이 바뀌지 않아야 한다.
- 결과 표시 직전 누르고 있던 키가 자동 재시도/종료로 이어지지 않아야 한다.
- 모달을 닫은 뒤 유효한 항목으로 복귀하고 이전 화면으로 되돌아갈 수 있어야 한다.

위 검사는 실제 UI 구현에서 수행할 계획이다. 특정 접근성 표준 준수·스크린리더 호환·지원 해상도 인증은 아직 확인하지 않았다. 지원할 보조 기술과 대상 해상도/배율은 실제 런타임 능력과 사용자 요구를 확인한 뒤 별도 명시한다.

## 20. 학교·공용 Windows PC의 첫 실행 검수와 최소 진단

**후속 상태 안내:** 아래 초기 미감지 기록 이후 연결 표시가 확인됐다. 최신 관측과 남은 축 배정 확인은 20-7절을 따른다. 초기 미감지 원인이 해결됐다고 확정하거나 비행 성공으로 확대하지 않는다.

사용자가 학교 Windows PC에서 공개 빌드 수동 실행을 시도한 상황을 반영한다. **2026-10-28 사용자 제공 화면으로 게임 설정 화면 표시와 Windows `joy.cpl` 장치 목록이 비어 있음을 확인했다.** 화면 표시만 확인한 것이며 키보드 비행·조종기 보정/비행은 미검증이다. 조종기는 미감지 상태이고 원인은 아직 확인하지 않았다. 조종기는 후속 사용자 확인으로 Boxer이며 케이블·데이터 포트·USB 선택 세부는 확인 중이다.  목록이 비었다는 사실만으로 게임 결함·장치 고장·학교 보안 차단 중 하나를 원인으로 확정하지 않는다. 공개 배포 기준은 v0.7.4-r2이나 해당 실행본의 정확한 ZIP/버전 일치 확인은 별도로 남긴다. 스크린샷의 개인정보는 이 문서에 옮기지 않는다. 이 절은 QA-08/12, REL-04/07, DOC-07, OPS-02/09에 연결하는 외부 환경 검수 계획이다. [기존 다른 PC 실행 안내](PORTABLE_QUICK_START.ko.md)를 대체하지 않고 관리형 PC의 승인·중단·진단 범위를 보완한다.

### 20-1. 실행 허가와 호환성은 별개다

- 학교/기관의 설치·프로그램 실행·USB 사용 정책과 사용 권한을 먼저 확인한다. 개인이 파일을 내려받았다는 사실을 관리형 PC에서 실행할 권한으로 간주하지 않는다.
- 보안 제품·Windows 경고·기관 정책으로 차단되면 화면의 정확한 메시지와 발생 단계를 기록하고 담당자 확인으로 넘긴다. 백신/방화벽/정책 해제, 관리자 암호 공유, 파일명 변경 등을 통한 우회를 안내하지 않는다.
- 필수 구성요소 설치·드라이버 업데이트·관리자 승인이 필요하면 허가된 담당자 절차로 진행한다. 권한이 없으면 환경상 미실행으로 기록하고 개인 장치 등 허가된 환경의 시험을 별도로 검토한다.
- 공개 실행 안내의 OS/GPU 조건은 지원 대상 설명이지 해당 PC 호환 인증이 아니다. 해시 일치 또한 코드 서명·안전성 또는 기관 실행 승인을 대신하지 않는다.
- 설치/진단 과정에서 다른 사용자의 파일이나 학교 관리 설정을 변경하지 않는다. 공유 계정의 보정/기록은 다른 이용자와 섞일 수 있으므로 사용자 데이터 보존/정리 권한을 확인한다.

### 20-2. 단계별 확인과 멈출 지점

| 단계 | 확인할 최소 내용 | 실패 시 분류·다음 행동 |
|---|---|---|
| 파일 준비 | 공개 버전·ZIP 이름, 전체 압축 해제 여부, 실행기와 필요한 폴더 존재 | 소스 ZIP/부분 복사/다운로드 미완료를 구분. 검증 안 된 다른 출처 파일로 대체하지 않음 |
| 실행 허가 | 학교 PC에서 실행 가능한지, 표시된 차단/승인 요청 | 정책 제한이면 담당자 확인. 게임 결함으로 확정하지 않음 |
| 실행기 시작 | 실행기 표시/오류, 필수 구성요소 안내, 게임 프로세스 시작 여부 | 실행기 이전/이후 단계 구분. 관리자 실행을 만능 해결책으로 제시하지 않음 |
| 게임 화면 | 초기 화면·글꼴·해상도/배율·그래픽 오류·즉시 종료 여부 | GPU/드라이버/권한 등은 가설로 기록. 화면 미표시를 조종기 오류와 섞지 않음 |
| 수동 키보드 확인 | 실제 배포본 안내대로 키보드 선택·수동 준비/비행·종료 | USB 장치가 없으면 키보드 범위만 검수. 전체 조종기 검증으로 확대하지 않음 |
| USB 확인(가능 시) | 허용된 장치 사용, 실제 입력 검출·모드·보정·저장 | 장치 부재/정책 차단/입력 미검출을 구분. 기존 다른 사람 보정 복사 금지 |
| 저장·재실행 | 현재 계정에서 설정/진단 쓰기 가능 여부, 재실행 상태 | 저장 실패와 게임 실행 실패를 별도 기록. 공유 계정 데이터 삭제는 별도 허가 필요 |

자율 브리지 실패와 수동 조종 가능 여부는 따로 관찰한다. 기존 안내는 자율 연결 실패 시 수동 조종 가능성을 설명하지만, 이 PC에서 실제로 가능한지는 직접 확인 전 확정하지 않는다. 학교 네트워크나 방화벽을 열어 자율 기능을 강제로 시험할 필요는 없다.

### 20-3. 먼저 받을 최소 피드백

처음부터 전체 로그/사용자 폴더를 요구하지 않고 다음 항목으로 실패 단계를 좁힌다.

1. 실제 ZIP/표시 버전과 어느 단계까지 진행했는지.
2. 화면의 오류 문구 또는 필요한 부분만 잘라낸 화면. 사용자명·학교 계정·학생 정보·다른 창은 가린다.
3. Windows 버전/시스템 종류, GPU 모델·드라이버 정보는 해당 증상에 필요할 때만 추가한다. 장치 일련번호·PC 자산번호는 기본 수집하지 않는다.
4. 입력 방식(키보드/조종기), 조종기 기종·Mode 1/2와 실제 관찰. 하드웨어 고유 식별자/개인 보정 원본은 제외한다.
5. 정상 기대 동작, 실제 동작, 반복 가능한 최소 순서, 재시도 여부.
6. 설치/실행 권한 제한이 있었는지. 관리자 암호나 기관 보안 설정 파일을 전달하지 않는다.

이 정보로 부족할 때만 해당 실행 시각의 관련 로그 일부·진단 파일의 필요한 필드를 요청한다. 로그에 사용자 경로·장치 식별값 등이 포함될 수 있으므로 공유 전에 확인한다. 원본 보존이 필요하면 허가된 로컬 위치에 두고, 공유용 사본만 필요한 범위로 줄인다. 공개 이슈 업로드는 별도 확인 없이 수행하지 않는다.

### 20-4. 결과 상태와 개인정보 최소화 검수

| 관찰 결과 | 보고 표현 |
|---|---|
| 정책/관리자 승인 문제로 실행 전 중단 | “기관 승인 대기·게임 실행 미검증” |
| 게임 화면은 표시, 비행은 안 함 | “화면 실행 확인·수동 비행 미검증” |
| 키보드 수동 비행만 확인 | “해당 PC 키보드 범위 확인·USB 미검증” |
| 조종기 검출만 확인 | “장치 검출 확인·보정/연속 비행/재연결 미검증” |
| 오류 원인 특정 불가 | “증상/단계 확인·원인 조사 필요” |
| 로그/진단 공유 불가 | “진단 접근 제한”과 관찰 가능한 범위만 기록 |

진단 내보내기 개선을 구현할 때는 파일명/포함 항목/저장 위치를 미리 보여주고 자동 전송하지 않는 원칙을 유지한다. 허용 목록 기반 축약본에 개인 보정·전체 사용자 경로·계정/기밀값이 포함되지 않는지 검사한다. 축약 실패나 저장 실패를 공유 완료로 표시하지 않는다. 현재 배포본에 이런 자동 비식별화 기능이 있다고 주장하지 않는다.

**검수 출구:** 실제 환경·권한/차단·파일 출처·도달 단계·입력 방식·증거와 미검증 범위를 구분해 기록한다. 한 학교 PC의 성공/실패를 모든 학교 PC의 지원/비지원으로 일반화하지 않는다. 사용자에게 추가로 요청할 정보는 다음 진단 판단에 필요한 것만 선택한다.


### 20-5. 장치 미감지 안내의 분기와 복귀 계약

12절은 앱 안의 연결·보정 오류를 다루지만, Windows에서 확인한 결과와 앱이 직접 관측한 결과를 혼합하지 않도록 다음 분기를 추가한다. **아래는 새 한국어 도움말의 기획이며 현재 실행본의 자동 진단 기능이 아니다.** 기존 기능/후보 번호를 추가하지 않고 C01~C03과 연결한다.

| 사용자에게 한 단계씩 요청할 확인 | 답에 따른 다음 화면·중단 조건 |
|---|---|
| “Windows 게임 컨트롤러 목록에 조종기가 보이나요?” | 보임 / 비어 있음 / 확인 못 함을 구분. 사용자의 답은 ‘사용자 확인’으로 표시하고 앱이 Windows 전체 상태를 자동 검사했다고 표현하지 않음 |
| 목록이 비었거나 확인 못 함 | 조종기 정확한 모델, 사용한 USB 단자·기기에 표시된 USB 모드를 먼저 확인. 모델별 공식 안내를 확인하기 전 특정 메뉴·단자를 정답으로 단정하지 않음 |
| 연결 구성을 확인할 수 있음 | 기관 허용 범위에서 데이터 연결이 확인된 케이블 또는 허용된 다른 포트 등 한 조건씩 바꾸고 목록을 다시 확인. 무엇을 바꿨는지와 결과를 짝지어 기록. 충전 표시만으로 데이터 연결 성공 판정 금지 |
| Windows 목록에는 보이나 입력 반응을 확인하지 못함 | 해당 장치의 스틱 반응 확인 단계로 안내. 목록 등록을 네 독립 축·올바른 배치·앱 호환 완료로 확대하지 않음 |
| Windows에서 반응하지만 앱 목록/입력에는 없음 | 앱 다시 찾기와 지원 입력 경로 대조로 분기. 케이블 교체·보정 반복만 계속 요구하지 않고 ‘Windows 확인 / 앱 입력 미확인’을 함께 표시 |
| 변경 권한이 없거나 계속 미감지 | ‘확인 중단·담당자 문의’ 또는 ‘키보드로 진행’ 선택 제공. 키보드 검수와 USB 문제를 분리하고 기존 저장 보정을 지우지 않음 |

드라이버 교체·펌웨어 갱신·장치 초기화를 기본 복구 버튼으로 제공하지 않는다. 필요성이 확인되면 장치별 공식 안내와 기관 허가를 별도로 확인한다. 원인이 미확인인 상태에서 사용자가 반복 보정을 완료해야만 빠져나갈 수 있는 구조도 피한다.

**문구와 증거의 출처:** 앱의 “연결된 조종기를 찾지 못했어요”는 현재 앱 검색 결과에만 연결한다. 도움말에는 “Windows에서도 보이지 않는다면 연결 방식부터 확인해요”처럼 조건문을 사용한다. ‘케이블 불량’, ‘드라이버 없음’, ‘학교에서 차단’은 확인된 근거 없이 자동 원인으로 출력하지 않는다. Windows 확인 시각/사용자 응답과 앱 재검색 결과는 별도로 갱신하며, 이전 응답으로 새 연결 상태를 덮어쓰지 않는다.

**복귀 검수 시나리오**

- Windows 확인을 건너뛰거나 권한상 확인하지 못해도 ‘확인 못 함’으로 종료할 수 있고, ‘장치 없음’ 또는 사용자 실패로 변환하지 않는다.
- Windows 목록 빈 상태→장치 표시→앱 재검색의 순서에서 현재 단계와 다음 행동만 바뀐다. 장치 표시만으로 보정 완료·USB 활성·ARM 성공 알림을 띄우지 않는다.
- Windows에서는 반응하지만 앱에서 미검출인 시험 조건에서 연결 도움말을 무한 반복하지 않고 지원 입력/앱 단계 조사로 넘어간다. 이 조건은 별도 재현 시험이며 현재 학교 PC에서 관측한 사실이 아니다.
- 목록 재검색 중 USB가 바뀌거나 같은 이름의 장치가 늘어나면 새 결과를 명시적으로 선택하게 하고 이전 장치/보정을 임의 적용하지 않는다.
- 도움말에서 돌아와도 선택한 과제·기존 저장 보정은 보존하고 현재 입력 조건을 다시 검사한다. ‘다시 찾기’, 도움말 닫기, 키보드 선택이 자동 ARM·비행 재개를 일으키지 않는다.
- 실제 접속 확인 뒤에도 축/스로틀·보정·명시적 연결 및 준비 절차는 기존 안전 계약대로 수행한다. 진단 단계 통과를 안전 게이트 면제로 쓰지 않는다.

검수 결과는 문구/분기 fixture, 실제 Windows 장치 상태, 앱 입력, 실물 비행 결과를 나누어 남긴다. 이번 계획 추가는 학교 PC의 미감지 원인을 해결하거나 새 연결 시험을 수행했다는 뜻이 아니다.


### 20-6. 비교 장비가 없을 때의 진단 보류

2026-10-28 후속 사용자 확인: 조종기는 Boxer이며, 재연결 뒤 Windows 장치 목록에서 변화가 관찰되지 않았고 PC의 다른 USB 포트에서도 같은 증상이 보고됐다. 다른 케이블은 없어 교차 비교하지 못했다. 정확한 조종기 데이터 포트 사용 여부·USB 선택 세부와 원인은 여전히 미확인이다. 이는 사용자 관찰 기록이며 USB 버스 전체가 응답하지 않는다는 계측 결과나 케이블 불량 판정이 아니다. 다른 포트 확인을 다른 PC에서 재현한 것으로 확대하지 않는다.

기획상 '재시도해도 동일'과 '비교 수단이 없어 미실행'을 분리한다. 도움말에서 “다른 케이블이 없어요”를 선택하면 같은 교체 지시를 반복하지 않고 **“케이블 비교는 나중에 확인해요. 지금까지 확인한 내용은 유지해요.”**라는 보류 경로를 제공한다. 구매·드라이버 변경·기관 설정 변경을 필수 다음 단계로 강제하지 않는다.

- 진단 재개 카드에는 마지막 관측 단계, 바꾼 조건, 동일/달라짐, 미실행 비교와 필요한 수단만 남긴다. 학교/PC 식별 정보·원본 스크린샷은 필요하지 않다.
- 재개 시 케이블·포트·USB 선택이 이전과 같은지 확인하고 달라진 조건은 새 관측으로 기록한다. 이전 미감지를 현재 결과로 고정하거나 여러 조건 변경 후 하나를 원인으로 확정하지 않는다.
- 수용 검수: 비교 수단 없음→보류→앱 종료/재진입에서 미실행 항목이 실패/완료로 바뀌지 않고, USB 검증 미완료 상태와 키보드 진행 선택이 독립적으로 유지돼야 한다. 진단 카드 저장 지원은 구현 계획이며 현재 배포본의 저장 기능으로 약속하지 않는다.


### 20-7. 연결 이후 축 배정 불일치 관측과 재확인

**2026-10-28 후속 관측:** 앞의 미감지는 당시 기록으로 보존한다. 이후 제공된 설정 화면에는 USB 연결 상태, 키보드 활성, 보정 완료 표시와 함께 YAW=Z / THROTTLE=R 배정이 보였다. 사용자는 실제 왼쪽 스로틀 움직임이 Z, 러더 움직임이 V라고 보고했다. 화면 표시와 사용자 관찰의 배정이 일치하는지 재확인이 필요하며, 두 화면/API의 축 이름이 같은 기준인지도 확인해야 한다. 자동 매핑 오류·저장 보정 재사용·장치 출력 변경 중 어느 것이 원인인지 아직 확정하지 않았다. 배정 수정·USB 입력 활성·비행 성공은 미확인이다.

이 사례는 12절의 ‘장치 연결됨’과 ‘입력 검토 완료’를 더 명확히 나눌 근거다. **보정 완료 표시는 저장된 값의 존재/검증 상태일 수 있으며 현재 물리 스틱과의 일치를 대신 증명하지 않는다.** 안내 제안은 “연결은 확인했어요. 비행 전에 스틱 움직임을 하나씩 확인해 주세요.”다.

- 검토 화면에서 물리 스틱 위치/움직임 → 현재 앱이 관측한 축 → 배정된 Roll/Pitch/Yaw/Throttle → 정규화 방향을 한 줄로 대조한다. 외부 화면의 Z/V/R 글자만 보고 앱의 같은 글자에 자동 배정하지 않는다.
- 실제 스틱 하나만 움직여 해당 채널이 의도한 방향으로 반응하는지 확인한다. 스로틀 최저와 나머지 중립을 별도로 확인하고, 다른 채널까지 움직이면 축 중복·동시 움직임·출력 구성의 확인 단계로 돌린다.
- ‘저장 설정 불러옴’과 ‘이번 연결의 스틱 확인’은 별도 상태로 표시하는 방안을 검토한다. 장치 이름이 같거나 저장 보정이 유효해도 사용자에게 현재 배정과 변경 여부를 확인할 수 있게 한다.
- 수정은 기존 안내 보정/검토 경로로 수행하고 취소 시 이전 저장값을 보존한다. 새 배정·반전이 바뀌면 해당 범위/중립·스로틀 조건을 다시 검증하고 이전 완료 표시를 그대로 재사용하지 않는다.
- 인수 사례: 저장 보정은 유효하지만 실제 출력 축 배치가 달라진 합성 조건에서 ‘저장됨’만으로 확인 완료를 표시하지 않아야 한다. 축 이름 대조→단일 스틱 확인→필요 시 재보정→저장→명시적 USB 활성 순서를 검수하며 ARM은 별도다. 이 사례의 실제 재현 시험은 아직 수행하지 않았다.

이 개선은 모든 연결에서 무조건 전체 재보정을 요구하는 정책이 아니다. 정상 프로필의 재사용 편의는 유지하되 현재 입력과 불일치가 관측되면 안전하게 검토/수정할 수 있어야 한다. 원본 개인 보정·학교 장치 식별 정보·스크린샷은 공개 문서에 옮기지 않는다.


**미설정 기본값의 표시 계약 — 2026-10-28 정적 확인:** [보정 구조체](../Source/ImperialWingsSimulator/RadioCalibration.h)의 초기 배정은 Roll X / Pitch Y / Yaw Z / Throttle R이고 범위·중립·확정 플래그는 거짓이다. 따라서 이 축 조합 자체는 장치에서 자동 탐지됐다는 증거가 아니다. 학교 화면의 같은 배정이 초기값 때문인지 저장값 때문인지는 별도 확인하며, 화면의 보정 완료 표시와 혼동해 원인을 확정하지 않는다.

한국어 기본 화면은 미확정 상태에서 초기 축 번호를 정답처럼 강조하지 않고 “아직 확인하지 않았어요 — 스틱 설정을 시작해 주세요”로 안내한다. 고급 화면에서 초기값을 보여줄 필요가 있으면 ‘초기값·미확인’을 명시한다. 저장값을 불러온 상태, 이번 안내 보정에서 감지한 상태, 검토 후 확정한 상태를 실제 내부 근거에 맞춰 구별한다. Mode 1/2 선택만으로 축 탐지 완료로 바꾸지 않는다.

인수 사례에 **프로필 없음→초기 배정 표시→모드 변경→설정 취소**, **저장 프로필 불러오기**, **안내 보정 완료**를 나란히 둔다. 각 화면의 배정 출처·확정 상태가 맞고 미설정 첫 경우에 ‘자동 감지 완료/보정 완료’가 표시되지 않아야 한다. 이는 새 UI 검수 제안이며 현재 화면 결함을 재현하거나 수정한 결과가 아니다.

### 20-8. 스틱 반응이 느리다는 후속 피드백

2026-10-28 사용자는 **“해보니까 스틱 반응이 너무 느린거 같아”**라고 보고했다. 앞서 설정 화면에서 약 17 FPS가 관측됐지만, 이는 해당 화면의 순간 표시이며 비행 중 FPS·입력 지연 측정값이 아니다. 후속 질문에 사용자는 **“바로 움직이긴 하는데 회전·이동 속도가 둔한 느낌”**이라고 설명했다. 따라서 현재 사용자 체감 분류는 반응 시작 지연보다 즉시 반응 후 회전·이동 응답이 둔한 쪽이다. 이는 정량 지연 측정이나 입력 지연이 전혀 없다는 증거는 아니다. 비행 중 FPS·축별 입력 크기·실제 회전/이동 속도·원인·개선 효과는 미확인이다. 축 수정 성공·전체 비행 검수 완료나 저성능이 원인이라는 결론으로 확대하지 않는다.

기존 6절과 [프레임별 제어 비교 계획](fixed-step-control-design.md)에 이 사례를 연결한다. 별도 감도/물리 변경 전에 다음 최소 관측으로 조사 경로를 나눈다.

| 확인할 관측 | 다음 진단·해석 제한 |
|---|---|
| 물리 스틱과 앱 입력 막대의 변화가 함께 늦거나 끊김 | 장치 표본·폴링·표시 프레임을 구분. 막대 애니메이션만으로 USB 자체 지연을 확정하지 않음 |
| 막대는 반응하지만 기체의 반응 시작이 늦음 | 실제 입력 적용·제어/물리 갱신·렌더 표시의 시각 연결 검토. 동기화 없는 화면 관찰을 정밀 지연 수치로 사용하지 않음 |
| 반응은 바로 시작하나 회전/상승 등이 둔함 | 어느 축인지, 같은 입력 크기인지, ANGLE·스로틀 직접/정밀·출력 제한 등 실제 조건부터 기록. 감도나 물리 계수 부족으로 즉시 단정하지 않음 |
| 화면 전체가 끊기고 당시 프레임도 낮음 | 동일 장면/입력의 프레임 시간과 기존 제어 비교 절차로 확인. 설정 화면의 17 FPS를 모든 비행 조건의 대표값으로 쓰지 않음 |

입력 막대 확인은 우선 DISARM 상태에서 하고, 비행 비교는 축/방향·안전 준비가 확인된 뒤 허가된 조건에서 수행한다. 첫 질문은 “입력 표시도 늦나요, 아니면 기체만 둔하게 움직이나요?”처럼 한 번에 구분 가능한 행동으로 제시한다. 재현 전 임의 감도 상승·데드존 제거·출력 제한 해제로 체감을 덮지 않는다. 원인·변경 효과·사용자 체감 개선은 각각 별도 증거로 남기며 이번에는 측정이나 수정 시험을 수행하지 않았다.


### 20-9. 다른 Windows PC에서도 연결 가능한 첫 설정 — 사용자 요청

사용자 요청: **“다른 PC에서도 실행 했었을때 연결이 가능하도록 해줘.” / “계획서에도 추가해줘.”** 목표는 검증된 지원 환경에서 새 PC로 옮겨도 한국어 안내로 장치 확인·스틱 설정·저장·안전한 조종 준비를 마칠 수 있게 하는 것이다. C01~C03, INP-02~13, QA-08/12의 기존 범위에 연결하며 모든 PC·USB 기기 호환이나 무설정 연결을 보장하지 않는다.

기존 20-1~7절의 진단을 재사용하되 **PC 간 이동**을 독립 인수 경로로 둔다.

| 이동/변경 조건 | 요구되는 동작·검수 |
|---|---|
| 같은 조종기, 다른 실제 Windows PC, 저장 설정 없음 | Windows 인식→앱 장치 목록→실제 스틱 축/방향 탐지→보정 검토→해당 PC 저장→명시적 USB 활성·ARM 준비까지 한국어로 안내. 개발 PC의 축 번호/보정 파일을 전제로 삼지 않음 |
| 같은 PC에서 USB 포트·연결 순서 변경 | 장치 목록 인덱스를 영구 정체성으로 간주하지 않음. 실제 선택 장치와 입력을 다시 대조하고 다른 장치로 조용히 바뀌지 않게 함 |
| 같은 이름의 장치 또는 다른 조종기 | 이름/기종만으로 저장 보정을 강제 적용하지 않음. 사용자 선택과 한 축씩 움직임으로 확인, 모호하면 선택/보정 안내 |
| 저장 후 앱 재실행·USB 분리/재연결 | 저장 프로필과 현재 장치/모드/축·스로틀 조건 재검증. 저장 성공과 활성·ARM을 구분하고 자동 비행 금지 |
| 데이터 케이블·데이터 포트·USB 모드 미확인 또는 Windows 미인식 | 20-5~6절 진단/보류 경로. 앱만으로 OS 미인식을 해결한다고 약속하지 않으며 기관 정책 우회·무단 드라이버 설치 금지 |
| 저장 권한 제한·공용 계정 | 실패 원인과 다음 행동 표시, 다른 사용자 설정 덮어쓰기 금지. 보정 이식/공유는 별도 검증 전 기본 기능으로 제공하지 않음 |

**호환 검수표 제안:** 실제 PC별 Windows/입력 경로·앱 버전, 장치 기종·모드, 연결 구성, OS 검출/앱 검출/네 독립 축·방향/보정/저장·재실행/비행·손실 복구를 별도 열로 기록한다. 다른 기종은 같은 표의 별도 행으로 시험하고 특정 Boxer의 통과를 모든 HID·게임패드로 확대하지 않는다. 장치 식별값·계정명·개인 보정 원본은 공개 표에 넣지 않는다.

**수용 경계:** 새 폴더나 새 사용자 데이터만으로 다른 PC 검수를 대신하지 않는다. 지원 대상은 실제 확인한 입력 경로와 환경 범위로 명시한다. 장치 검출만 성공한 행은 연결 준비 단계까지만 인정하고 비행/재연결은 미검증으로 남긴다. 조종기·PC 조합과 실제 시험 일정은 아직 정하지 않았으며, 이번 요청은 개발 목표의 기획 반영이지 호환 기능 구현·실물 시험 완료 보고가 아니다.


**현재 WinMM 구현과 개선 경계 — 2026-10-28 정적 대조:** [장치 열거/선택 코드](../Source/ImperialWingsSimulator/ImperialRadioSubsystem.cpp)는 슬롯·제조사/제품 값·이름·보고 기능/축 범위를 조합한 `winmm-v1` 식별값을 사용한다. 코드가 읽는 WinMM 정보에는 장치 일련번호가 없으므로 이 값은 물리 기기의 영구 고유 ID가 아니다. 슬롯 변화로 식별값이 달라지면 재선택/보정이 필요할 수 있으며, 다른 PC로 보정이 자동 이전되는 구현도 아니다. 기존 안내 보정·저장·명시적 활성은 활용하되 새 식별/이식 기능이 이미 있다고 설명하지 않는다.

검수에 다음 두 경우를 구분한다: (1) 같은 기기가 다른 슬롯으로 바뀌어 기존 프로필이 일치하지 않는 경우, (2) 같은 슬롯에 보고 속성이 동일한 다른 기기가 들어와 식별값만으로 구별할 수 없는 경우. 첫 경우는 기존 저장값 손실로 오인하지 않게 재설정 이유를 안내하고, 둘째 경우는 프로필 일치 표시만으로 같은 물리 기기라고 단정하지 않는다. 두 경우 모두 20-7절의 현재 스틱 확인과 실제 선택이 필요하다.

새 입력 백엔드·영구 장치 식별·프로필 이식 도입은 별도 설계/회귀 검수 대상이다. 기본 연결 개선을 위해 현재 식별 비교를 느슨하게 하거나 이름만 맞으면 보정을 적용하는 우회는 채택하지 않는다. 위 두 사례는 예정된 시험이며 실제 기기를 바꿔 재현하지 않았다.


## 21. AI 팀끼리 관전하고 내 팀을 훈련하기 — 추가 후보, 2026-10-28

사용자 요청: “인공지능끼리 대결하는것도 구경하고싶어 내가 인공지능 팀을 학습 시키는것도 좋을거 같아”. 기존 C15와 AI·TEAM·관전 분야의 확장 후보로 연결하며 **326개 기능·C01~C16 번호를 늘리지 않는다.** 한국어·간편 조종기 설정을 우선하고 이 절은 구현·시험 완료가 아닌 후속 기획이다.

### 21-1. 현재 근거와 새 범위

[공개 태그의 AI 대전 설명](https://github.com/sun475300-sudo/Drone-Soccer-Simulator/blob/v0.7.12-rc1/docs/ai-duel-2026-10-28.md)은 사람의 파란 공격수 1대 대 빨간 AI 3/4대의 비대칭 로컬 훈련, 종료 결과 저장을 보고한다. [같은 태그의 통합 계획](https://github.com/sun475300-sudo/Drone-Soccer-Simulator/blob/v0.7.12-rc1/docs/master-development-plan.md)은 기본 관전/관객/심판 시점을 기반으로 적고 사람 팀 동료·5대5 협력을 후속으로 둔다. **기본 카메라와 기존 AI 상대가 있다는 사실만으로 양 팀 완전 AI 관전·협력 학습 구현을 확인한 것은 아니다.** 이번 확인은 공개 문서 대조이며 실행·소스 전체 감사·실물 시험이 아니다.

사후 기록을 설명하는 [AI 코치](ai-coach-detailed-plan-2026-10-28.md)와, 경기 행동을 결정하는 팀 AI를 분리한다. 코치의 한국어 추천이 곧 정책 변경·학습 실행·성능 향상의 증거는 아니다.

일시정지·배속은 후속 검토다. 일시정지를 제공한다면 경기 시계·물리·AI 판단·기록의 동일 정지 계약을 먼저 검수하고, 배속으로 물리/입력 주기를 바꾼 결과를 실시간 경기와 동등하다고 표시하지 않는다. 자동 카메라 연출은 판정과 독립적이며 자유 시점으로 복귀 가능해야 한다.

### 21-3. “훈련” 방식 구분과 단계

1. **우선 제안 — 전술 설정/반복 평가:** 공격·수비 성향, 위치/역할 책임, 복귀 우선순위 등 실제 구현된 허용 매개변수만 한국어로 조정한다. 동일 팀을 여러 조건에서 시험하는 것은 규칙 기반 튜닝이며 “신경망이 학습했다”고 부르지 않는다. 조정 가능한 값·상한은 물리/규칙 검토 후 결정한다.
2. **후속 후보 — 시범 기반 학습:** 사용자가 명시적으로 기록한 조작과 관측에서 정책을 학습하는 방식. 데이터 동의·조종권·장치 보정·품질·정답 정의가 선행되며 잘못된 보정/연결 손실 구간은 학습 근거로 채택하지 않는다.
3. **후속 후보 — 강화학습/자가대전:** 격리된 시뮬레이션에서 정책을 갱신한다. 관측·행동·보상·종료 조건·학습 예산·체크포인트·복원과 보류 평가 환경이 먼저 필요하다. 득점만 보상해 충돌/규칙 악용·복귀 회피를 강화하지 않도록 유효 판정·안전·중단 사례를 별도 검수한다.

학습 중인 후보와 실제 관전 경기에 쓸 채택 정책을 분리한다. 규칙·득점 판정기·물리 한계는 정책이 수정할 수 없다. 외부 임의 스크립트/모델 실행·실기체 제어·자동 온라인 업로드는 이번 범위가 아니다. 파일 형식·크기·버전/해시·허용 입력/출력을 검증하고 호환되지 않는 정책은 기존 검증 프리셋으로 명시적 복구한다.

### 21-4. 비교 측정과 개발 인계

- 경기마다 빌드/물리/규칙, 팀 구성·역할·정책 버전, 시드, 난이도/지각 정보, 경기 시계, 정상/중단 이유와 확정 점수를 저장한다. 기존 16~17절 사건·정정·중복 방지 계약을 재사용한다.
- 승/무/패와 득실, 유효 공격/복귀, 충돌·복구 실패·가드 상태, 실행 시간·프레임 상태를 분리한다. 수집하지 못하는 지표는 미측정이며 접촉 횟수를 전술 성공으로 대체하지 않는다.
- 전후 정책은 같은 평가 조건 묶음·양 진영 교환·여러 상대/초기 조건에서 비교한다. 학습용과 보류 평가용 조건을 분리하고 특정 상대에만 적응한 결과를 일반 실력 향상으로 표현하지 않는다.
- 시드가 같아도 강체 물리와 프레임 조건으로 궤적/득점이 달라질 수 있다. 반복 횟수·허용 편차·최소 개선 기준은 기준 측정 후 합의하며 임의 수치를 성공 기준으로 확정하지 않는다.
- 개발 의존성: 양 팀 AI 조종권/참가자 관리 → 역할별 행동과 복귀·판정 사건 → 관전 입력 격리 → 결과/정책 저장 → 기준팀 비교 → 별도 승인된 ML 실험. 인원이 늘어난 협력은 기존 1 대 3/4 성능으로 검증을 갈음하지 않는다.

| 검수 시나리오 제안 | 통과 기대 |
|---|---|
| 양 팀 AI 시작·관전 시점 변경·중복 시작 | 참가자/소유권 일치, 중복 경기 없음, 수동 조종/ARM 유출 없음 |
| 유효 통과·복귀 전 재접근·비참가 기체 | 실제 규칙 판정과 UI/결과 일치, 목표점 도착만으로 득점 없음 |
| 중단·복구 실패·경기 종료·새 경기 | 중단을 승리로 기록하지 않음, 이전 점수/명령/정책이 다음 경기에 남지 않음 |
| 정책 저장 실패·손상·다른 버전·학습 취소 | 정상 채택 정책 보존, 오류 원인과 재시도/복원 제공, 미완료 후보를 완료로 표시하지 않음 |
| 같은 결과의 관전 화면·비교표·선택형 코치 | 동일 확정 사건과 분모 사용, AI 경기 성적을 사용자 수동 조종 성적으로 합산하지 않음 |
| 평가 중 자원/예산 한도 도달 | 새 작업 중지·검증된 체크포인트 보존, 완료/부분/실패 구별, 무한 재시도·자동 유료 확대 없음 |

위 시나리오는 **아직 실행하지 않은 인수 계획**이다. 재현 데이터·기대값·검사 결과를 따로 남긴 뒤에만 완료 처리한다.

### 21-5. 비용·미결정과 MVP 경계

권장 MVP는 **로컬 규칙 기반 AI끼리 관전 + 전술 프리셋 복제·비교**다. 양 팀의 지원 인원/역할은 기존 비대칭 구조를 확장하는 난도를 확인하고 확정하며 처음부터 완전한 5대5 협력·ML을 약속하지 않는다. USB 미연결 관전은 가능한 목표지만 수동 모드로 전환할 때 조종기 준비·안전 게이트를 건너뛰지 않는다.

로컬도 CPU/GPU·메모리·저장 공간·전력·소요 시간을 사용한다. 학습은 별도 자원/시간 예산과 중지 버튼을 두고 관전/조종 프레임을 방해하지 않도록 격리한다. 클라우드 학습 비용은 장비 시간×단가+저장/전송+운영 비용으로 별도 산정하며, 사후 코치의 설명 API 비용과 합치지 않는다. 공급자·가격·성능은 미정이며 이 기획으로 유료 자원 실행을 승인하지 않는다.

결정할 사항: 첫 팀 인원과 역할 범위, 사용자가 조절할 전술 항목, 공정한 AI 지각 정보, 관전 중 일시정지/배속, 팀/정책 저장·복원 UI, 로컬 지원 사양·예산, ML 필요 여부와 방식·데이터 동의·평가 검토자. 우선 규칙 기반 시제품을 관찰한 뒤 실제 학습의 가치를 판단한다.


## 22. 사용자 리포트·개발/운영 분리·선택형 업데이트 — 2026-10-28 추가 기획

사용자는 개발 환경과 사용자 환경을 나누고 사용자 리포트를 개발 측에서 신속히 확인하는 방안 및 우선 필요한 기능 목록을 요청했다. **현재 별도 개발/운영 서버·자동 접수·업데이터가 구축됐다는 뜻이 아니다.** 서버를 만들기 전에 로컬 진단과 수동 검토 경로부터 설계하며, 기존 번호·후보와 18절 배포 무결성·20절 최소 진단 원칙을 재사용한다.

### 22-1. 먼저 필요한 기능과 선행 조건

| 순서 | 작업 묶음 | 완료 판단에 필요한 근거 |

### 22-2. 신고 화면과 전달 상태

흐름: **도움말/문제 신고 → 현상·재현 순서 입력 → 포함 자료 미리보기/제외 → 전송 목적·수신자·보관/삭제 안내 → 이번 신고 전송 동의 → 접수 결과 → 처리 상태 확인.**

- 필수 최소 자료는 버전/빌드 지문·발생 기능·기대/실제 동작·재현 단계·오류 코드다. 기기/OS 정보는 필요한 범주만 선택하고 불명은 불명으로 둔다. 20-3절 진단 허용 목록을 재사용한다.
- 기본 제외: 계정/학교/사용자 이름, 전체 경로, 조종기 고유 식별자·개인 보정 파일, 비밀/키, 전체 원본 비행 로그. 화면·로그는 선택 첨부이며 공유 전 확인/가림이 필요하다. 자동 비식별화만으로 완전 익명이라고 보장하지 않는다.
- 자유 입력·파일·URL은 비신뢰 자료다. 형식/크기/압축 해제 한도·악성 파일·경로 탈출을 검사하고 격리한다. 보고서 내용을 개발 명령·코드·자동 패치·학습 데이터로 실행하지 않는다.
- 전송 거절·오프라인·서버 미구축이어도 로컬 저장/복사와 기존 시뮬레이터 사용을 막지 않는다. 담당 접수 창구가 정해지기 전 가짜 “전송 완료”나 실제로 없는 주소를 표시하지 않는다.
- 상태는 **초안 / 전송 중 / 서버 접수됨 / 개발 검토 대기 / 검토 중 / 추가 정보 필요 / 해결 후보 있음 / 사용자 확인 완료 / 종료**를 구분한다. 접수번호는 수신 측 확인 후 표시하며 알림 전송만으로 개발자가 읽었다고 간주하지 않는다. 해결 후보 배포는 사용자 환경의 해결 확인과 별개다.
- 시간 초과는 접수 여부 미확정이다. 동일 신고 식별자로 상태 확인/재전송하고 중복 접수를 합친다. 일시 장애만 제한된 지연 재시도, 인증/검증 실패는 수정 안내. 한도·보관 기간은 운영 결정 후 확정하며 무한 재전송이나 앱 재시작 후 무동의 업로드 금지.
- 연락처는 답변을 원하는 경우 별도 선택·보관하며 진단 본문과 분리한다. 익명 접수 조회를 제공한다면 추측 불가능한 조회 수단과 접근 통제가 필요하다. 접수번호만으로 남의 첨부를 열지 못해야 한다.

### 22-3. 개발/운영 환경 간 안전한 전달

목표 구조는 **사용자 앱 → 운영 접수 경계 → 검증/민감정보 제거·격리 → 최소 신고 요약 큐 → 개발 검토함**이다. “바로 전달”은 검증된 요약의 신속한 알림을 뜻하며 사용자 PC가 개발 서버에 직접 접속하거나 운영 DB 전체가 개발 DB로 복제되는 구조가 아니다.

- 개발/시험/운영의 저장소·자격 증명·권한·알림 목적지를 분리한다. 동일 물리 장비여도 접근 경계를 검수하며 개발자의 모든 운영 원문 열람을 기본값으로 두지 않는다.
- 개발 검토함에는 재현에 필요한 축약본과 제한된 근거 링크만 전달한다. 원본 첨부는 운영 격리 영역에 두고 사유/권한에 따른 접근과 감사 기록을 적용한다. 알림 채널에는 개인정보·원문 첨부·조회 비밀을 싣지 않는다.
- 전달 작업은 서비스별 최소 권한·인증된 암호화 통신과 고정 허용 목적지를 사용한다. 재시도/실패 대기열과 접수→전달 식별자를 연결해 누락·중복을 감지한다. 개발 서비스가 내려가도 운영 접수 결과를 거짓 실패/완료로 바꾸지 않는다.
- 개발 재현은 합성 또는 비식별 자료를 우선한다. 운영 데이터로 자동 ML 학습·코치 API 전송은 금지하며 신고 동의는 다른 학습/분석 목적의 동의가 아니다.
- 운영 반영은 코드 검토·시험·검증된 배포 산출물·승인/롤백 절차를 거친다. 신고 도착이나 개발 서버 수정만으로 사용자 실행본을 자동 교체하지 않는다.
- 보관 만료/삭제 요청은 첨부·축약본·개발 복사·캐시·백업 만료 범위를 추적한다. 실제 삭제 범위와 남는 보안 감사 기록은 안내하고 즉시 완전 삭제를 근거 없이 약속하지 않는다.

### 22-4. 사용자가 고르는 업데이트와 별도 설치

현재 공개 배포는 전체 ZIP을 새 폴더에 푸는 방식이다. **기존 설치 업데이트 / 별도 버전 설치 / 나중에**는 제안 사용자 선택이며 현재 자동 업데이터가 있다고 안내하지 않는다.

1. 버전·정식/사전 배포 채널·변경점·미검증 범위·필요 공간·설정 호환을 먼저 보여준다. 사전 배포는 명시적으로 선택하며 비행 중 업데이트 실행/재시작을 강제하지 않는다.
2. **기존 설치 업데이트:** 앱 종료와 대상 경로를 확인하고 개인 설정을 별도 보존한 뒤 검증된 전체 산출물을 준비한다. 부분 덮어쓰기 금지. 실패 시 기존 실행본/설정을 보존하고 성공 확인 후 전환한다. 초기 MVP는 새 폴더 설치 후 사용자가 전환하는 수동 절차로 제공 가능하다.
3. **별도 설치:** 실행 폴더·바로가기·버전을 명확히 구분한다. 같은 Windows 사용자에서는 두 폴더가 같은 사용자 설정 경로를 사용할 수 있으므로 “새 폴더=설정 격리”라고 표시하지 않는다. 버전별 데이터 저장소/명시적 가져오기 구현 전에는 병행 사용의 공유 설정 위험과 백업/복원 절차를 안내한다.
4. 설정 가져오기는 원본 읽기·호환 검사·사용자 확인·새 사본 저장 순서다. 지원하지 않는 새 형식을 이전 버전에 억지로 읽히거나 원본을 조용히 변환하지 않는다. 기존 보정 복사만으로 USB 활성화/ARM하지 않고 실제 장치와 축 방향을 다시 확인한다.
5. 업데이트 메타데이터/파일의 신뢰 출처·무결성·버전/대상 플랫폼을 검증한다. SHA-256 일치만으로 출처 인증이 완성됐다고 주장하지 않는다. 서명·신뢰 메타데이터 방식과 키 관리/복구는 구현 전 결정한다.
6. **되돌리기:** 실행본뿐 아니라 설정 스키마/기록 호환도 확인한다. 새 기록은 보존하고 호환 불가를 안내한다. 검증되지 않은 다운그레이드를 “안전 복원”으로 표시하지 않는다.

### 22-5. 인수 시험·운영 미결정

| 제안 시험 | 기대 결과 |
