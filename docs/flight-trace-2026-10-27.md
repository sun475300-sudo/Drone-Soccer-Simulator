# 비행 전 구간·전류·전력 비교 — 2026-10-27

**기존 물리 관찰기를 켜고 끈 실행의 모든 기록 프레임을 비교했다.** Editor·Shipping의
여섯 게임 갱신 간격과 새 압축 해제본을 합쳐13쌍·26회 비행을 검사했다. 각 쌍의 CSV는
바이트 단위까지 같았고, 초기화 구간을 포함한 모델 전하·전력 적산도 일치했다.

이번 완료 범위는 **현재 동기 게임 물리프레임 기준의 관찰 전후 비교**다. 물리 스레드로
제어기를 옮기거나 고정120Hz 비행을 구현한 작업은 아니다. 개발 브랜치는
`codex/r9-solver-probe`, 일반 실행용 다운로드는 기존 v0.7.4-r2를 유지한다.

## 구현과 독립 검증

`-ImperialFlightTrace`를 명시한 물리 검사에서만 기록 actor를 생성한다. 마지막 물리 계산이
끝난 `PostPhysics`에서10대의 위치·Quaternion·선속도 벡터·각속도·ARM/자율 상태·입력·
전류·소비 전하·잔량·전압·공급/모터 전력을32개 CSV 열에 기록한다. 부동소수점은17자리
정밀도로 저장한다. 기존 힘·토크·PID 경로와 물리 설정은 바꾸지 않는다.

기체에는 진단용 물리 갱신 순번과 배터리 초기화 번호를 추가했다. 두 표본 사이의 갱신
순번이 정확히1씩 증가하는지 검사해 누락·중복을 찾는다. 기체0이24·27·30초에 초기화되는
기존 검사에서는 배터리 누적값도 초기화되므로, 구간별 값을 분리한 뒤 전체 소비량으로 합친다.
나머지9대의 DISARM 상태 전자장비 소비도 기록한다.

첫 행은 비교 기준으로만 사용하고 그 이전 초기 구간은 적산에서 제외한다. 이후 각 행의
실제 `FlightModelSeconds` 차이를 `dt`로 사용한다. 모델이 해당 단계의 전류를 적용하므로
사다리꼴 평균 대신 아래 직사각형 합을 독립 Python 분석기에서 다시 계산한다.

```text
전하(Ah) = Σ(현재 단계 전류 × dt / 3600)
전달 에너지(J) = Σ(전압 × 전류 × dt)
모터 전기 에너지(J) = Σ(적용 모터 전력 × dt)
```

각 단계의 소비 전하 증가량과 잔량 감소량도 확인한다. 초기화 단계에서는 누적 전하의
기준을0, 초기 잔량을1로 놓는 **이 검사 시나리오의 ResetDrone 계약**을 따른다.
전압은 모델이 계산한 값을 직접 읽으며, 감소한 뒤의 잔량으로 같은 단계의 전압을 다시
계산하지 않는다. 원시 double 잔량·전압 getter를 추가했고 기존 float API는 유지한다.

종료 순서는 비행 검사 완료 신호 → 마지막 PostPhysics 기록 → CSV 저장·닫기 → 결과 JSON →
관찰기 완료 순서다. 관찰기에는 기록 actor를 선행 Tick으로 지정해 마지막 프레임이 빠지지
않도록 했다. 행 수110,000개·게임 시간45초 제한을 두고, 잘못된 모드 조합은 거부한다.

새 한글·공백 폴더에 압축을 푼 Shipping의60FPS 비교도 통과했다. 합계13쌍·26회,
기체 상태937,400행이며 첫 기준 행을 제외한 기체별 시간 구간은937,140개다.
13쌍 모두 원본 CSV SHA-256이 같았다. 위치·속도 벡터·각속도·전기값·적산 차이는0이다.
Quaternion으로 각도를 다시 계산할 때는 같은 입력에서도 정규화·내적·acos의 반올림으로
최대`2.98e-8rad`가 나왔다. 비교 한계`1e-4rad` 안이며 기록된 Quaternion 값의 차이는 없다.

60FPS의 기록 범위는 월드 시간 약0.033333335~43.016668910초다. 비행 시나리오는 게임
시간43초에 끝나며, 첫 기준 표본 이후의 적산 구간은 약42.983335575초다.
기체0의 세 번 초기화를 모두 합산한 모델 소비 전하는 약0.1526968603Ah,
전달 에너지는8,855.9076J, 모터 전기 에너지는8,640.4409J였다.
단계별 전하 증가량과 독립 적산의 최대 오차는 약`6.94e-18Ah`였다.

모든 비행 검사에서 호버·바닥/벽/네트 접촉·실제 골대 통과를 포함한 기존 검사도 통과했다.
60FPS 호버 오차는3.15cm이며 청팀1득점과 오프사이드를 확인했다. 다른 FPS의 개별 수치는
검증 JSON에 보존했다. 계측을 위해 비행 중 위치를 보정하거나 실제 조종기 입력을 만들지 않았다.

## 실패 재현과 보완

- 초기 비교는 전력 한도를 절대`1e-5W` 오차로 검사해 실패했다. 실제 적용 추력은float,
  공급 예산은double이므로 추력으로 재계산한 전력이 약18.5µW 차이 났다. `P ∝ T^1.5`
  관계와 float 반올림에서 유도한 `1e-8 + 3×2^-24×max(적용전력, 가용전력)` 범위만
  허용하도록 했다.320W에서 약57µW이며 물리 공급량을 늘린 수정이 아니다. 이 범위를
  넘기는 모터 전력 오염은 별도 시험에서 거부했다.
- 각 프레임의 모터 전력도 비교한다. 두 프레임의 증가·감소가 최종 적산에서 상쇄되는
  오염을 넣어, 합계만 같다고 통과하지 않음을 확인했다.
- 누락·중복·순서 변경·마지막 프레임 삭제·NaN/Infinity·초기화/물리 순번 오류·전하 상쇄·
  전압×전류와 전달 전력의 불일치·속도 방향 반전·잘못된 요약·빈 관찰 결과 등17가지 오류를 거부했다.
  같은 회전인 `q`와`-q`는 허용했다. **분석기 시험은18종**이다.
- 실제 옵션 검사6개에서 단독 trace·고정 solver·불완전한 관찰 조합·CSV 경로 누락·
  잘못된FPS·기존CSV를 거부했다. UE5.8의 generic writer가
  `FILEWRITE_NoReplaceExisting`을 처리하지 않아 시험용 기존 파일이 덮인 현상을
  재현했다. 명시적 파일/디렉터리 존재 검사로 보완했고 시험 원본의 바이트 보존을 확인했다.
  실행 도구는 매번 새 고유 폴더를 사용한다. 서로 다른 프로세스 사이의 원자적 파일 소유권을
  제공하는 기능으로 주장하지 않는다.

## 배포·기록·재실행

최종 소스 내용 지문은
`71aa36b021080fcbc262ed1820ba6d169e7d3fc36651e3978beb690a2eb8515e`(127개 입력)다.
Editor/Shipping을 다시 빌드한 뒤 전체 비교를 재실행했다. 기존 solver 계측12조건과
거부4조건도 같은 지문에서 다시 통과했다. 빌드에는 부모`0e0dd21`과 수정 표시가 들어 있으며,
이후 게시 커밋이 이미 내장됐다고 표시하지 않는다.

새 압축 해제본은13개 배포 검사와60FPS 전 구간 비교·18종 분석기 검사를 통과했다.
실제 조종기 보정은 변경하지 않았고 배포 폴더에 개인 설정·기록이 들어가지 않았음을 확인했다.
로컬 QA 파일 `ImperialWings-Windows-v0.7.5-dev-trace-r2.zip`은374,810,923바이트,
SHA-256은 `33ec007b00d6e1075690ad2cb1c8096330af1aeda207dbc37de27643870df67c`다.
이 파일은 새 일반 사용자 릴리스로 공개하지 않는다.

```powershell
.\.venv\Scripts\python.exe Tests/run-flight-trace.py --engine '<UE 설치 폴더>' --corruption-checks
.\.venv\Scripts\python.exe Tests/run-flight-trace.py --packaged --package-root '<새 압축 해제 폴더>\Windows' --corruption-checks
.\.venv\Scripts\python.exe Tests/test-flight-trace-options.py --package-root '<새 압축 해제 폴더>\Windows'
```

단계1의 비교 범위를 마지막 상태에서 **모든 동기 게임 물리프레임의 경로·모델 적산**으로
확장했다. 내부 Chaos 서브스텝 상태나 수학적으로 연속인 궤적을 계측한 것은 아니다.
이 결과를 바탕으로 다음 단계의 입력/상태 전달·기체 수명 관리·단일 힘 경로 이관을 진행한다.
새 경로의 실제 고정120Hz 비행·60초 및 지연 시험·실물 조종기·다른 물리PC·GPU/실사 그래픽 검증은 남아 있다.
