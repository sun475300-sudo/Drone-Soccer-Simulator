# CTL-13 단계2 준비: 입력 버퍼와 실제 힘 적용 연결

2026-10-27, `codex/r9-solver-probe`, v0.7.5-dev. 이번 작업은 **별도 단순 강체로 상태 전달과
힘 적용 연결을 검사하는 하위 단계**다. 기존 드론의 센서·PID·모터·배터리 계산을 아직
새 경로로 이관하지 않았다. 공식 다운로드 v0.7.4-r2는 그대로이며 새 일반 사용자
릴리스로 배포하지 않는다.

## 구현과 독립 정답

`-ImperialSolverBridgeSmoke`에서만 충돌·중력·감쇠가 없는 반지름0.25m·질량2kg의
별도 구체를 생성한다. 초기 자세는 회전시켜 두며 초기 속도는0이다. 경기장의 드론10대는
계속 DISARM이고 기본 ANGLE·LOS·물리 설정·추진력 계산은 바꾸지 않는다.

게임 스레드는 순번·발행 시각·기체 세대·ARM·힘·작용점 오프셋의 복사본을 입력 버퍼로
전달한다. 실제 Chaos 내부 핸들은 물리 callback에서만 읽고, 완료된 출력 버퍼를 통해
게임 스레드로 반환한다. callback은 UObject·조종기·HUD에 접근하지 않는다.

각 solver 단계에서 적분이 정확히1회인지 확인하고 적분 직전에 힘·토크를 각각 한 번
적용한다. 뉴턴은 Unreal의kg·cm/s²로100배, N·m는kg·cm²/s²로10,000배 변환한다.
적분 이후에는 갱신된 선속도·각속도를 읽는다. 이 hook의 `X/R`은 아직 최종 위치·자세가
아니므로 적분 뒤 위치로 표시하지 않는다.

독립 Python 분석기는 callback이 보고한 적용 여부를 정답으로 삼지 않고, 아래의
미리 정한 명령 순서를 기준으로 실제 속도 변화를 검사한다.

| 구간 | 발행한 입력 | 요구되는 결과 |
|---|---|---|
|0|DISARM|힘·토크0|
|1|새 ARM|힘(2,-1,0.5)N|
|2|DISARM|힘·토크0|
|3|발행 시각을 solver 시간보다1초 전으로 설정|유효 기간0.1초 초과로 차단|
|4|바인딩 세대1에 세대2 명령|차단|
|5|힘에 실제NaN 입력|차단; JSON에는0 벡터와 비유한 입력 표지를 기록|
|6|첫 표본은 같은 번호·새 내용, 이후는 더 오래된 번호1|두 재전송 모두 차단|
|7|새 순번의 ARM|정상 힘 재개|
|8|DISARM|힘·토크0|

각 구간은 약0.5초다. 전환은 게임 프레임 끝에서 하므로 노출 시간은 해당FPS의
프레임 경계 오차를 허용한다. 같은 입력 표본을 여러 solver 단계가 재사용할 때는
원래 발행 시각을 유지한다. 새로운 발행은 입력 번호도 증가해야 하며, 거부한 표본은
다음 서브스텝에서도 계속 거부한다.

작용점은 질량중심에서 월드축(0,0.05,0)m 떨어져 있다. 적용 구간의 토크는
(0.025,0,-0.1)N·m다. 균질 구체의 관성은 `I=2mr²/5=0.05kg·m²`이며 실제 내부
질량·관성을 이 값과 대조한다. 매 단계 `Δv=F·dt/m`, `Δω=τ·dt/I` 및 처음부터의
누적 속도 변화를 독립 계산한다. 게임 시간과 solver 시간 합, 입력 발행/소비 순서,
모든 단계의 유한값·호출 수·명령 구간을 함께 검사한다.

마지막에는 body를 유지한 채 callback을 해제하고 소멸 확인을 기다린다. 종료 표지가
설정되면 callback은 내부 핸들 접근·힘 적용을 중단한다. 소멸 뒤에는 남은 힘·토크 때문에
속도가 바뀌지 않는지 확인한다. 실제 body 파괴 후 새 proxy로 재바인딩하는 시험은 아니다.

## 자체 검토와 수정

1. 새 발행인데 입력 번호가 이전과 같은 경우, 시각과 내용을 바꿔 받아들일 수 있는
   경로를 검토에서 발견했다. 새 발행의 순번을 엄격히 증가시키고 거부 상태를 표본마다
   유지하도록 고쳤다. 구간6에서 같은 번호·새 내용과 오래된 번호를 따로 시험한다.
2. 최초 패키징은 기본 객체 생성 중 질량을 설정하며 엔진 초기화 전에 물리 재질을
   조회해 실패했다. 질량 설정을 진단 검증 후 실제 `BeginPlay`로 옮겼다. 첫60FPS
   실행 성공은 이 수정과 재전송 보완 전의 예비 결과이며 최종 결과로 재사용하지 않는다.
3. 분석기는 힘이 실제 적용되지 않아도 callback의 플래그만으로 통과하는 것을 막는다.
   각 구간 노출 시간·발행 원본과 소비 표본·프레임 간격·누적 속도·최종 장부를 따로
   대조하고, 손상한 결과를 거부하는 검사도 포함한다.
4. 병렬 실행 두 개가 같은 Windows 시각 문자열을 받아 결과 폴더 생성이 한 번 거부됐다.
   기존 폴더를 재사용하거나 덮어쓰지 않았으며, 실행기 폴더 이름에 임의 식별자를 더해
   충돌을 피하도록 수정했다. 이후 Editor와 새 압축 해제본은 이 실행기로 검사했다.

## 재현 방법

```powershell
.\.venv\Scripts\python.exe Tests/run-solver-bridge.py
.\.venv\Scripts\python.exe Tests/run-solver-bridge.py --packaged
# --package-root <압축 해제 폴더>\Windows 로 새 경로의 Shipping도 검사한다.
```

실행기는 최대90초의 프로세스 제한, 별도 사용자 저장 폴더, `-nullrhi`를 사용한다.
결과 원본과 실행 로그는 고유한 `Saved/Verification/solver-bridge-*` 폴더에 남긴다.
정상 사례는 종료 코드0과 결과 JSON을 모두 요구한다. 의도적인 옵션 거부는 기존
Windows 엔진의 정상 종료 특성을 고려해 종료 코드0/1에 더해 구체 오류와 빌드 지문을
필수 검사한다.

## 범위와 다음 관문

- 동기 solver 단계의 실제 힘 연결 시험이며 정확한120Hz 비행 제어 완료가 아니다.
- 구체의 질량중심은 원점과 같다. 중심이 치우친 실제 드론의 관성·접촉·로터·전력·PID
  연결, 초기화/파괴/재바인딩, 비동기 수명과10대 후류는 후속 시험이다.
- stale 구간은 시뮬레이션 시각을 의도적으로 오래되게 만든 표본이다. USB 지연,
  실제 입력 단절·멈춘 게임 스레드의 실시간 watchdog, 실제 포커스 손실을 검증하지 않는다.
- 미래 시각·누락 표본을 거부하는 방어 코드는 있지만 이번9구간에서 직접 실행한
  거부 사례로 세지 않는다. 기본 상태는 DISARM이다.
- GPU 화면·실사 품질·실물 조종기·다른 물리 PC 시험으로 해석하지 않는다.

다음 작업은 이 연결 방식에 **한 대의 실제 비행 모델을 분리해 이관**하고 기존 힘 경로를
확실히 끈 상태에서 호버·ANGLE 복원·전력·정지를 확인하는 것이다.
[단계별 전체 설계](fixed-step-control-design.md)를 따른다.

설치된 UE5.8.3 소스의 `Chaos/SimCallbackObject.h`, `SingleParticlePhysicsProxy.h`,
`PBDRigidsEvolutionGBF.cpp`, `ChaosVehicles/DeferredForces.cpp`와 공식
[TSimCallbackObject](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Chaos/TSimCallbackObject),
[FSingleParticlePhysicsProxy](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Chaos/FSingleParticlePhysicsProxy)
문서를 함께 확인했다. 엔진 버전이 달라지면 내부 API와 실행 순서를 다시 검증한다.
